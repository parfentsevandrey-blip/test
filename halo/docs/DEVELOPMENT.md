# Ореол: для разработчиков

Как собрать, проверить и выпустить Ореол, и как он устроен внутри. Для
пользователей — [README](../README.md).

## Сборка

```sh
cargo build --release           # target/release/halo
```

Нужен [Rust](https://rustup.rs). На Windows рядом с `halo.exe` должен лежать
`wintun.dll` с [wintun.net](https://www.wintun.net) (папка `bin/amd64`).

Android: нужны Rust, `cargo-ndk`, Android SDK и NDK 29. Затем
`cd android && ./gradlew assembleDebug`. Gradle сам соберёт Rust-ядро и
Kotlin-привязки. `-PhaloAbis=x86_64` собирает только под эмулятор. Версию
приложения Gradle берёт из `Cargo.toml` (`[workspace.package]`), одну на весь
проект: `1.2.3` становится `versionName` 1.2.3 и `versionCode` 10203.

## Тесты

```sh
cargo test                      # кадры, адреса, журнал, сопряжение, статус, лог
cargo build && sudo scripts/netns-test.sh
```

`cargo test` сопрягает устройства через loopback: совпадение эмодзи, отказ,
неверный код, уход одной стороны, отмена на телефоне во время подключения и во
время ожидания ответа.

`netns-test.sh` поднимает три узла в сетевых неймспейсах Linux на виртуальном
коммутаторе и проверяет:

- пинг в обе стороны и полноразмерные пакеты 1280 байт с запретом фрагментации;
- скорость через iperf3;
- что устройство не из сети не может достучаться;
- восстановление после штатного перезапуска и после падения узла (`kill -9`).

Набор запускается трижды: участники с адресами на каналах с MTU 1500; то же на
«узких» каналах с MTU 1300, где полноразмерный пакет туннеля не помещается в
одну датаграмму и обязан фрагментироваться; участники только по `id`, без единого
адреса, когда узлы находят друг друга через mDNS.

Четвёртый набор проверяет журнал. `b` и `c` сопряжены только с `a`, находят друг
друга через его журнал и пингуются. Затем `a` удаляет `c` на ходу: `b` узнаёт об
удалении и отключает `c`, а `c` больше не достучаться ни до кого.

Пятый набор проверяет связь вне дома. `a` и `b` стоят за домашним роутером с NAT,
который раздаёт пробросы портов по NAT-PMP (`scripts/natpmp-router.py`, как
настоящий роутер: правила DNAT в iptables). `c` знакомится с ними дома, затем
переезжает в «мобильную» сеть за другим NAT без пробросов. `c` дозванивается
до обоих по публичным адресам, которые они объявили, примерно через секунду после
смены сети. `sudo scripts/netns-test.sh outside` запускает только его.

Шестой набор — якорь. `a` дома за роутером с NAT-PMP, `b` в «кафе» и `c` в
«мобильной сети», оба за NAT без пробросов. `b` и `c` дозваниваются до `a`, узнают
от него свои публичные адреса и пробуют пробить NAT навстречу друг другу. Linux-NAT
из теста (как и роутеры на OpenWrt) такой встречный звонок не пропускают: пакет,
пришедший первым, занимает порт, и ответ уходит с другого. Поэтому пакеты между
`b` и `c` идут через `a`, и набор это проверяет.

Результаты в контейнере (release-сборка, один поток iperf3, TCP). Все узлы на
одной машине, так что это верхняя граница ядра, а не обещание для телефона:

| Канал | Пинг через туннель | Скорость | Фрагментация |
|---|---|---|---|
| MTU 1500 | ~0,8 мс | 1,14 Гбит/с | нет |
| MTU 1300 | ~0,8 мс | 567 Мбит/с | каждый полноразмерный пакет |

Smoke-тест (`scripts/smoke-test.sh`) проверяет то, что получает пользователь,
на настоящих macOS, Windows и Linux (systemd) в CI: устанавливает собранную
программу службой, сопрягает её с `echo-peer`, ждёт соединения и пингует его
адрес системным `ping`. Пакеты идут через TUN-устройство системы, узел и
QUIC-соединение и обратно. Затем установка поверх (обновление на месте) и
`halo uninstall`, после которого не должно остаться ни службы, ни файлов
программы.

## CI и релизы

CI (`.github/workflows/halo.yml`) на каждый push: rustfmt, clippy и юнит-тесты
на Linux, macOS и Windows; сквозной тест в сетевых неймспейсах Linux; сборки для
трёх систем со smoke-тестом каждой; APK (debug и release), Android Lint и
сквозной тест на эмуляторе Android (`scripts/android-e2e.sh`). В нём телефон
сопрягается с узлом A на машине CI по коду, проходит системный диалог согласия
на VPN и пингует узел через туннель, а узел — телефон. Узел B в отдельном
сетевом неймспейсе с телефоном не сопрягался: телефон узнаёт о нём из журнала A,
перестраивает маршруты туннеля и достаёт до B, а B пускает телефон.

Релиз: поднять версию в `Cargo.toml` (`[workspace.package]` и зависимости
`halo-core`), обновить `docs/RELEASE_NOTES.md`, затем запустить workflow
**halo** на этом коммите с параметром `publish_release` (событие
`workflow_dispatch`: кнопка Run workflow во вкладке Actions, если workflow есть в
ветке по умолчанию, или запрос к GitHub API). Когда все проверки пройдут, задача
`release` соберёт файлы в релиз
`halo-v<версия>`: `halo-macos.tar.gz`, `halo-linux-x64.tar.gz`,
`halo-windows-x64.zip`, `halo-android.apk` и `SHA256SUMS`.

APK подписывается одним и тем же ключом, иначе Android не поставит новую версию
поверх старой и данные приложения (ключ устройства) пропадут. Ключ лежит в
черновике релиза `halo-android-signing-key`: черновики видят только те, у кого
есть право записи в репозиторий. Первый релиз создаёт ключ и черновик сам
(`scripts/sign-apk.sh`). Черновик нельзя публиковать и удалять.

## Устройство кода

```
crates/
  halo-core/          ядро: общее для десктопа и Android
    src/addr.rs       адрес в сети из ключа
    src/frame.rs      формат датаграмм, фрагментация и сборка
    src/node.rs       узел: TUN, соединения с участниками, mDNS, проверки
    src/journal.rs    журнал участников: подписанные записи и кто в сети
    src/presence.rs   где устройство достать из интернета: подписанные адреса
    src/sync.rs       обмен журналом и адресами между участниками
    src/wire.rs       общее кодирование подписанных записей
    src/members.rs    участники и их имена
    src/state.rs      каталог с ключом и журналом
    src/pair.rs       сопряжение: код, доказательство знания секрета, эмодзи
    examples/echo-peer.rs  участник без TUN, отвечает на пинг (для smoke-теста)
  halo-cli/           CLI `halo` для Linux, macOS и Windows
    src/service/      служба: systemd, launchd, диспетчер служб Windows
    src/status.rs     отчёт работающего узла для `halo status`
    src/logfile.rs    лог службы с ротацией (macOS, Windows)
  halo-ffi/           привязки к Kotlin через UniFFI
android/              приложение: VpnService, Compose, сканер QR
scripts/
  netns-test.sh       сквозной тест в сетевых неймспейсах
  android-e2e.sh      сквозной тест на эмуляторе Android
  natpmp-router.py    роутер с NAT-PMP для сквозного теста
  smoke-test.sh       служба, туннель, обновление, удаление на настоящей ОС
  sign-apk.sh         подпись APK ключом Ореола (для релиза)
  build-android-rust.sh  ядро под Android и Kotlin-привязки (зовёт Gradle)
```

Протокол: ALPN `halo/0`. Каждая датаграмма начинается с байта-тега:

- `0` — дальше целый IP-пакет;
- `1` — фрагмент: `id` (u16, big endian), номер (u8), всего фрагментов (u8), данные.

Сопряжение: ALPN `halo/pair/0`, отдельный порт. Код `HALO/1/<ID>/<СЕКРЕТ>/<адреса>`
несёт ключ показывающего устройства, одноразовый 128-битный секрет и его адреса в
локальной сети. Сканирующее устройство подключается к этому ключу и доказывает
знание секрета: BLAKE3 с ключом из секрета от обоих ключей устройств. Затем
стороны обмениваются именами и портами узлов. Четыре эмодзи (24 бита) берутся из
экспортёра TLS этого соединения: при подмене посредником они разойдутся. Каждая
сторона отправляет «да» или «нет»; устройство добавляется, только если обе
сказали «да» и свой ответ дошёл до другой стороны. Уход или отмена на любом шаге
означают «нет» для обеих.

Журнал участников. У каждого устройства своя лента записей: «добавил устройство
(имя, адреса)», «удалил устройство», «меня зовут». Каждая запись подписана
ключом устройства (Ed25519) и ссылается на хеш предыдущей (BLAKE3), так что
подменить или переписать историю нельзя. Участники обмениваются тем, чего нет у
другого, по отдельному QUIC-потоку того же соединения, рядом с датаграммами
туннеля. Члены сети с точки зрения устройства — те, до кого оно доходит по
записям «добавил», начиная с себя, кроме удалённых. Все участники равны: любой
может добавлять и удалять. Удаление окончательное и отмечает, докуда автор видел
ленту удаляемого. Всё, что тот подпишет позже, ничего не значит, поэтому
удалённое устройство не может ни удалить других в ответ, ни привести новое.
Если два устройства удалили друг друга, не видя чужого удаления, удалены оба:
при сомнении журнал скорее удаляет, чем оставляет.

Присутствие («где меня достать»). Узел просит роутер о пробросе своего UDP-порта
(клиент `portmapper` от n0, протоколы определяются заранее: PCP, NAT-PMP, UPnP) и
собирает свои глобальные IPv6-адреса. Список публичных адресов он подписывает
своим ключом с номером версии и отдаёт участникам отдельным обменом `HPR1`. У
каждого устройства хранится последняя версия и, если та пустая, последняя с
адресами: ноутбук, ушедший из дома в кафе, остаётся достижим по домашнему адресу,
когда вернётся. Адреса не попадают в журнал, потому что они меняются, а журнал
вечный. Смена сети, при которой пропал прежний адрес, закрывает соединения и
сразу звонит заново по всем адресам: пока жив старый путь, iroh шлёт первые
пакеты нового соединения только по нему.

При обмене присутствием каждая сторона сообщает другой, по какому адресу её
видит. Публичный адрес, под которым устройство видно из-за его NAT, тоже попадает
в его присутствие: зная такие адреса друг друга, два устройства за NAT звонят
навстречу одновременно. Если это не удалось, работает пересылка: каждый узел
сообщает соседям (обмен `HLK1`), с кем соединён сейчас, и пакет для участника без
прямого соединения уходит тому соседу, который с ним соединён. Сосед передаёт
только пакеты самого отправителя и только напрямую подключённому адресату, ровно
один шаг. Пересылающий видит IP-пакеты (обычно внутри TLS приложений), поэтому
якорем служит только участник, то есть своё же устройство. Получатель принимает
пересланный пакет, только если пересылающий сообщил о соединении с его автором:
чужой адрес отправителя в пакете от соседа без такой связи считается подделкой.

Служба. `halo install` копирует программу в системный каталог
(`/usr/local/bin/halo` или `C:\Program Files\Halo` вместе с `wintun.dll`) и
регистрирует её: unit systemd с `Restart=on-failure`, демон launchd с
`KeepAlive` при ошибке, служба Windows с перезапуском при сбое. На Windows
программа сама говорит с диспетчером служб (`halo service`), адаптер Wintun
получает постоянный GUID, а правила брандмауэра (группа `Halo`) пускают транспорт
к `halo.exe` и трафик сети только на адрес устройства в Ореоле и только с адресов
Ореола. Работающий узел каждые пять секунд переписывает файл `status` в каталоге
состояния; `halo status` читает его, а отчёт старше 30 секунд считает узлом,
которого уже нет.
