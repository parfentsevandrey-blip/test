## Veil — Tor + Snowflake client for macOS 26 Tahoe

Liquid Glass UI, bundled Tor Expert Bundle (universal: Apple silicon + Intel), Snowflake / obfs4 / custom bridges, exit-country selection, live circuit and throughput, automatic system proxy.

### Fixed in 0.8.4 — the country filter runs before the list is cut, and the log is quiet
- **A pinned exit country still found nothing, and now it does.** 0.8.3 searched deeper but kept the same shape: take the widest exits, then discard the ones outside the chosen country. A country whose relays are not among the widest in the world still ended with nothing, which is what *"none of the 400 widest exits sits in GB"* was. The country is now resolved for a wide slice **before** the list is cut — several hundred relays in a handful of control round trips, because tor answers a multi-key `GETINFO` in one — and the filter picks the widest exits *inside* that country. If a country has only older exits, the requirement for conflux and congestion control is dropped for it rather than leaving it with none. When there genuinely is no exit there, the log now says how many relays tor could place, so the difference between "no exit in that country" and "geoip said nothing" is visible instead of guessed.
- **The SOCKS warning flood is really gone this time.** 0.8.3 set `WarnUnsafeSocks 0`, and tor 0.4.9 answered *"Skipping obsolete configuration option"* — the option was removed, so every probe kept warning. The probes now ask for `one.one.one.one`, `dns.google` and `dns.quad9.net` by name instead of by address, so there is nothing for tor to warn about. A name costs one resolve at the exit on a circuit's first probe and comes from the exit's own cache after that, and the warm-up sample that pays for it is discarded before a lane is ranked.

### Fixed in 0.8.3 — an exit country no longer switches Turbo off, and four log fixes
- **A pinned exit country left Turbo with nothing to do.** Veil looked for the video exit among the two dozen widest exits in the world and then kept only the ones in the chosen country. Pick a country with no relay in that global top — most countries — and the answer was always *"none of the widest exits fits the route's country rules"*: no exit pinned, so no video fan, no lane race and no measurement. The search now goes down the whole ranked list until it has enough candidates inside the chosen country, and says how many it looked at when there really is none. A relay's country is now read from the address the consensus already carries — one local lookup instead of two control round trips — so the deeper search costs no network at all.
- **Conflux is off behind Snowflake and meek.** Conflux exists to give one stream a second leg to the exit; behind a volunteer proxy or a CDN front both legs ride the same single link, so there is no second path to spread anything over — only twice the circuits to build through the one thing that is already the bottleneck, which is where *"Our circuit … died due to an invalid selected path, purpose Unlinked conflux circuit"* came from. Direct connections, obfs4 and custom bridges keep it.
- **The tonus no longer starves the video behind a bridge.** Snowflake or meek is often only a few hundred KB/s in total, and a 512 KB/s tonus took all of it: the stream failed over and over while the browser waited. Behind those transports it now runs at 128 KB/s — enough to keep the link from idling back to slow start, small enough to leave the video its share. Every other transport keeps the rate you set.
- **The SOCKS warning flood is gone.** Veil's latency probes connect to 1.1.1.1, 8.8.8.8 and 9.9.9.9 by address on purpose: those are constants in the source, nothing is ever resolved, and using a name would put the exit's DNS round trip inside the very number the probe measures. Tor cannot tell that apart from an application that leaked a lookup, so it warned on every probe — dozens a minute, burying everything else in the log. `WarnUnsafeSocks` is now off.

### Fixed in 0.8.2 — excluded countries no longer refuse every bridge
- **A tunnel that could never start behind a bridge.** With any country exclusion on — "Never route through", or "Avoid Five Eyes countries" — Veil sent the list to tor as `ExcludeNodes`, which tor also matches against the bridges themselves. Every bridge that fell in an excluded country was refused, one line per bridge in the log: *Not using bridge at […]: it is in ExcludeNodes.* With Snowflake, obfs4 or a bridge set from the Tor Project, that could mean every bridge refused and a connection that never came up at all. Present since 0.7.0, when exclusions stopped being gated on multihop.
- **The exclusion now applies where the choice is about.** Behind a bridge the list goes to `ExcludeExitNodes`: the exit — where the traffic actually leaves — is still never in an excluded country, and the bridge, which is the one hop you picked by hand, is left alone. A direct connection is unchanged and still excludes every hop. Switching between the two clears the other form, so a stale `ExcludeNodes` can never linger and refuse the bridges. The connect log says so once, and the Locations screen says it under the toggle.

### New in 0.8.1 — one video, many circuits
- **The video runs over every circuit at once.** YouTube binds its media to the address that fetched the page, so every video connection has to leave through one exit — which is why, until now, the whole YouTube family shared one circuit, and 4K was capped at that one circuit's throughput through Tor. But the exit is pinned by `MapAddress`, and a pinned exit is the same relay — the same IP — on *any* circuit. So Veil now spreads the video CDN (`googlevideo.com`) across every lane of the pool: four circuits, four different middle relays, all leaving through the one pinned exit. YouTube still sees a single address; the throughput is the sum. This is what lets the player's own logic see enough headroom to pick 4K and buffer far ahead instead of downshifting. The page and the API keep their single low-latency lane; only the heavy media fans out. Settings → YouTube shows how many circuits are carrying it.
- **Larger reads for the video.** The video CDN is now pulled from Tor in 256 KB slices instead of 64 KB, so a wide circuit is never left waiting on a localhost write between chunks.
- The fan is on whenever an exit is pinned and the lane pool is running — under Turbo 4K always, and for anyone using the wide video exit. It is off under per-site isolation, where each site keeps one circuit by choice, and whenever no exit is pinned, because then the circuits would leave through different addresses and the media would break.

### New in 0.8.0 — Turbo 4K, measured hop by hop
- **The video lane is raced.** With the exit pinned, every lane of the pool leaves through the same exit, so between them the only difference is the middle relay — the one hop nothing chose. Veil now pulls a public file through each lane for three seconds and binds YouTube to the widest; the circuit the measurement built is the very circuit the video then rides. Re-raced when that lane retires, and every fifteen minutes while nothing plays. The tile shows the lane's measured rate and the quality it sustains.
- **The guard is measured too.** Under Turbo on a direct connection, the three widest guards are timed one at a time — `EntryNodes` set to each, one stream on credentials of its own so tor builds a fresh circuit, proof from the circuit list that it went that way — through one wide exit that is the same for every guard, and the winner is pinned alone. A guard with no circuit for half a minute is let go before the browser notices.
- **The path is remembered.** The exit and guard that carried video last time are pinned again within seconds of the next connection, verified by one measurement, and kept while they carry at least 60% of what they did; only then is the race run again. The first Turbo connection pays for the measuring; the next ones start where it ended.
- **Modern relays only.** A video exit or guard must advertise conflux (`Conflux=1`) and congestion control (`FlowCtrl=2`), both tor 0.4.8: without the first there is no second leg, without the second a stream is capped at a fixed window's worth per round trip, whatever the relay's width. Exits must also carry port 80, which the measurement stream uses.
- **An exit the video CDN turns away is dropped.** The player that never buffers ahead and hangs is often not a narrow path but an exit Google refuses: every request answered in a few hundred bytes, connection after connection. The bridge now sees that pattern — several video-CDN connections through Tor closing almost empty within a minute, none carrying a video — and Veil switches to another exit at once, remembering the refused one for a week.
- **The tonus rides a circuit of its own.** Credentials of its own on Tor's port, so tor isolates it. The link it is there to warm is the one every circuit shares — the TCP connection to the guard or the bridge — and that link warms from any circuit; riding the video's own circuit, as it did, only took 4 Mbit/s out of the video's share and out of every measurement.
- **Measurements are longer under Turbo:** five seconds and up to 25 MB per candidate, five exit candidates instead of three, so a wide path is timed past its slow start. Turbo also sets four Snowflake proxies at once (on the next connection) and switches per-site isolation off, because the lane race runs across the pool's lanes; both go back when Turbo is switched off. A security preset that pins isolation now switches Turbo off, and says so.

### New in 0.7.11 — Turbo 4K: one button, everything through Tor
- **Turbo 4K.** One switch — on the YouTube tile, in Settings → YouTube, in the menu bar window, in the app menu (⇧⌘4) and as a Shortcut — for everything that makes YouTube fast through Tor, and nothing outside Tor: YouTube through Tor, the widest measured exit for every YouTube host, the widest entry guard (8K mode), the tunnel in tone at 512 KB/s or more the whole time the tunnel is up, conflux in throughput mode, traffic padding, multihop and relay pinning off, and circuits that keep taking new streams for half an hour instead of ten minutes (`MaxCircuitDirtiness`), with the measured lanes living twenty-five minutes to match — a video is one long session, and every move to a fresh circuit is a cold start. Pressing it while connected has the video path prove itself again at once; the tile then shows the measured rate and the quality it sustains.
- **Off means back, not defaults.** Turbo remembers what it changed and puts each setting back as it was when switched off. Changing one of the settings it manages by hand switches Turbo off and puts the rest back, so the switch always says what runs. A security preset lands on top of Turbo when it sets nothing the other way; one that does (Privacy first's padding, Speed first's YouTube outside Tor) switches it off and says so in the log.
- **What it cannot do, said where it is pressed.** Behind Snowflake or meek the bridge is the ceiling and no mode lifts it; the tile says so and names what 4K needs: a direct connection or obfs4. The entry guard chosen by capacity remains a finding on the Security screen, and its one-tap fix switches Turbo off.

### Changed in 0.7.10 — the tunnel in tone, as asked
- **512 KB/s, the whole time the tunnel is up, as one continuous stream.** 0.7.9 warmed the video circuit at 128 KB/s, only while a video played, and as a series of small requests — which is a series of gaps. As asked: the stream now runs at 512 KB/s by default (128, 256 and 1024 to choose from) for as long as the tunnel is up, and it is one continuous download of a large public file read in fixed slices ten times a second — the receive window holds the sender at exactly that rate, with no request/response gaps at all. When a file ends the next starts at once; when a source fails the next is tried. On the video's own circuit while a YouTube connection is open, on the main route otherwise, which shares the guard or bridge link with everything. "Only while a video plays" remains a choice.
- **A drop is acted on, not watched.** The stream is the gauge: once it has reached half the target, a quarter of the target held for half a minute — or the stream stalling outright — means the path under it dropped. The circuits are then retired so new connections get fresh ones, the route latency is re-measured and the video exit has to prove itself again; at most once every three minutes. The stream never gives up while it is wanted: a path that comes back is exactly the moment it must be there.

### New in 0.7.9 — the video circuit kept warm
- **A steady trickle on the video circuit while a video plays.** A player fetches a chunk, waits while the buffer drains, fetches again; in between, every hop's TCP connection idles, and Linux relays shrink their congestion window after an idle longer than one round trip. Each burst then ramps up from a small window again — the sawtooth on the speed graph, and the stall when a burst ramps too slowly to beat the buffer. While a YouTube connection is open through Tor, Veil now keeps a small steady stream on the same circuit — small requests to YouTube's image CDN a few times a second, riding the YouTube lane's own credentials so they share its circuit and its exit — and every hop stays at full window. Settings → YouTube: on by default at 128 KB/s, with 64, 256 and 512 to choose from; the caption says what the rate costs. The stream stops the moment the last YouTube connection closes and follows the lane the browser is on after a retirement.

### New in 0.7.8 — the video path, measured; an 8K mode; two tiles that say something
- **The video exit is chosen by what it carries, not by what it advertises.** After connecting, Veil now pulls a public file through Tor's own exit and through each of the three widest exits in turn, for four seconds each, and pins YouTube to the fastest — only if it beats Tor's own. The rate is shown in Settings → YouTube next to the quality it sustains (1080p from 5 Mbit/s, 4K from 22, 8K from 50), and a **Measure the video path** button repeats it on demand. Behind Snowflake or meek nothing is measured: the bridge is the ceiling, and the exit is verified rather than timed. The mapping that YouTube already has stays in place while candidates are measured, so a video playing meanwhile is not moved.
- **8K mode** (Settings → YouTube, off by default). On a direct connection the entry guard is the other end of the ceiling. With this on, Veil restricts Tor's entry guard to the three widest guards in the consensus and keeps the restriction only once a circuit through one of them has actually been built. It applies to every site, not only YouTube, and the Security screen counts it as a finding, because a guard chosen by capacity is a small, predictable set that every user of the mode shares. Bridges keep their own first hop, so behind Snowflake, obfs4 or meek the mode does nothing and says so. What no mode can do: make one Tor circuit carry more than the guard, the middle and the exit give it. 8K needs about 50 Mbit/s; the measurement says whether the path has it.
- **The latency tile works again.** With measured circuits on — the default since 0.7.0 — the route latency monitor was never started, so the tile said "Measuring…" for ever. It runs alongside the pool now.
- **The traffic padding tile says what the padding is doing:** the cover-traffic rate, its share of everything on the wire, the bytes sent and received through the onion loop, and one line on what the chosen level hides — instead of a level name and one number under a wave.

### New in 0.7.7 — a network that changes, a bounce nobody notices, bridges when nothing else works
- **A changed network is noticed, not just a lost one.** macOS reports a path as lost and restored, but a move from Wi-Fi to Ethernet, from one network to another, or a VPN coming or going often keeps the path "satisfied" the whole time — while the guard's TCP connection is already dead and every request hangs until something else notices. Veil now watches the interfaces and gateways the path runs over: when they change under a live tunnel, the tunnel is probed at once and bounced only if it fails; when they change after a failure, the next attempt comes in three seconds instead of at the end of the backoff.
- **A bounce holds requests instead of failing them.** During a soft reconnect — after a wake, a network change, a route failure — new connections used to be refused, so a page requested in those seconds showed an error. They are now held, unrouted and unanswered (nothing leaks), and let through when the tunnel is back: the page loads a few seconds later. The same hold covers the first seconds after a wake, while the tunnel is being verified. A hold ends on its own after half a minute.
- **Bridges from the Tor Project when every transport has failed.** On a network that is alive but blocks Snowflake, the built-in obfs4 bridges and meek, the automatic transport used to give up. It now does what Tor Browser's connection assist does: asks bridges.torproject.org — directly, then through a domain-fronted CDN — for the obfs4 and webtunnel bridges it recommends for this country, tries them at once, and keeps them, so the next connect on this network has them from the start. They appear in Settings → Bridges, with a button to forget them; the user's own bridge lines always take precedence.
- **Auto-reconnect backs off instead of hammering.** Consecutive failures wait 15, 30, 60, 120, 240 seconds and then five minutes between attempts; a success, a restored path or a changed network resets the count. With no network path at all nothing is retried — the path coming back schedules the retry itself.

### Fixed in 0.7.6 — fewer bounces, budgets that follow the clock
- **A network flap no longer cuts a working tunnel.** When the path was lost and came back while connected, a full reconnect was scheduled regardless — every circuit dropped for a Wi-Fi hiccup or an interface flap that had cost nothing. One probe after the path settles now decides, and only a tunnel that actually fails is bounced.
- **Budgets follow the clock, not the moment tor was warmed.** A standby can sit for hours; the consensus that was fresh when it started has a fixed lifetime, and the stage budgets set from the old freshness were too tight for the directory fetch the next connect had to make — a false stall on the first connect of the day. Freshness is now re-read from the clock at connect time.
- **The hard timeout spares an attempt that is still moving.** A directory fetch over a slow bridge could outlive the budget while bytes were still arriving. Past the budget an attempt is now abandoned only once it has also gone twenty seconds without progress, or has run twice the budget.
- **Ports picked hours ago are re-validated before use.** The SOCKS, HTTP and lane ports are chosen when the standby starts; anything on the Mac may take one meanwhile, and a taken lane port used to fail the whole connect. Each unbound port is checked and re-picked right before it is used, and a listener that fails to bind at activation is re-picked too.
- **"Connecting" counts as launched.** On a slow disk the consensus parse could hold the cold path past the launch deadline before any relay connection was even attempted; tor's own "connecting to a relay" now satisfies it, and the direct-connection deadline gains two seconds.
- **A first connection to a site gets 25 seconds, not 10.** Building a circuit, resolving the name at the exit and a slow server in a row could exceed the bridge's old deadline, and the browser then showed an error for a page that would have loaded. Onion services get 45.

### New in 0.7.5 — a browser that reveals less
- **Hardened browser window** (Security → Controls). What a site sees inside HTTPS — the browser and its version, the operating system, the languages, WebRTC's view of your address — is the browser's to reveal; a proxy cannot reach into an encrypted connection to change it, which is why an IP-check site still names your Mac and your Chrome behind a Tor exit. Veil now opens the browsers already on the Mac the way Tor Browser is built: a separate profile that goes through Veil only, WebRTC kept off the real address, QUIC off, and a generic identity — Firefox through its own fingerprinting resistance (`privacy.resistFingerprinting`: a Windows Firefox, a UTC clock, a standard screen, no WebGL), Chromium browsers (Brave, Chrome, Edge, Vivaldi, Chromium) through a fixed Windows user agent with client hints switched off. Nothing in the everyday profile is touched. The address is still a Tor exit, and every site can tell that it is one: that is Tor working, not a leak.

### New in 0.7.4 — YouTube through Tor, wide
- **One stream, two circuits.** Conflux was switched off whenever its latency mode was off. It is now always on, and by default in throughput mode: Tor builds two legs to the exit and the exit spreads a single stream over both — the only way one TLS connection, a video player's for instance, gets more than one circuit's share. Latency mode remains a switch in Settings → Route.
- **A wide exit for video.** A random exit is a random share of a random pipe. With YouTube through Tor, Veil now reads the consensus after connecting, takes the exits with the highest measured capacity that fit the route's country rules, and maps every YouTube host to the first one that actually carries a stream there (`MapAddress … .exit`, per destination — no global `ExitNodes`, no effect on any other site). The exit is re-verified every fifteen minutes and replaced if it stops answering. Settings → YouTube shows which relay it is; the switch is there too.
- **The whole YouTube session leaves through one exit.** YouTube binds its media URLs to the address that fetched the page, so the player on youtube.com and the video on googlevideo.com must share an exit — which, with a measured circuit per site, they did not. The YouTube host family is now one site for the lane pool, as Tor Browser's first-party isolation would have it.
- YouTube stays through Tor by default; the direct anti-throttling path is a choice in Settings → YouTube, and a choice made there is now remembered as one.

### Fixed in 0.7.3 — the probe advises, the relay decides
- **A censored network no longer gets its Wi-Fi reset for working.** The connectivity probe reaches public resolvers and a few well-known hosts; a network that blocks those can still carry Snowflake, whose rendezvous takes longer than the probe does. A "no Internet" verdict used to cut the attempt on the spot and then reset Wi-Fi. It now only shortens the attempt's leash — six seconds for a relay to answer — and a relay that answers, or real bytes arriving, overrules it: no abort, no Wi-Fi reset. The reset still fires where it belongs, on an attempt that reached nothing at all.
- **A relay answering counts as progress.** After a network hold the percentage stands still while tor talks to the guard; that conversation is now progress for the watchdog, so a slow guard is no longer mistaken for a stall.
- **Waking up asks the tunnel again once Wi-Fi is back.** After sleep the first health probe runs while Wi-Fi is still reassociating and fails for that reason alone. Once the network repair reports the Internet back, the tunnel is asked once more, and a guard connection that survived the nap is left alone instead of being bounced.
- **A tor that is still releasing its data-directory lock no longer fails the launch.** The cold path waits for a killed process to be gone before spawning, and retries once, a second later, if the lock is still held.

### Changed in 0.7.2 — the dashboard is the 0.6.1 one again
- **Home is back to the route diagram and the tiles.** The twelve-stage ledger that 0.7.0 introduced is gone; the dashboard is once more the power button with its status and chips, the live route (Mac → bridge → relays → Internet), and the tiles for speed, session, latency, protection, padding, routing, YouTube, apps and network. Everything under it — warm start, measured circuits, the Security section, the 0.7.1 connection fixes — is unchanged.

### Fixed in 0.7.1 — a connection that is only "connected" once a circuit exists
- **No more "connected" with nothing behind it.** After a hold — every disconnect, every failed transport, every soft reconnect keeps Tor loaded and offline — Tor's bootstrap counter and its `status/circuit-established` flag both stay at their high-water mark and say "done" before a single circuit exists. The second connect of a session could therefore flip to green in three seconds with no route under it, then watch its first page load stall. Veil now accepts "done" from a re-activated Tor only once a circuit has actually been built (a `CIRC … BUILT` event, or an open circuit in `circuit-status`, which lists live circuits alone), polls a second after activation instead of three, and brings the poll forward the moment a circuit completes.
- **A disconnect racing the launch standby no longer strands the next connect.** Stopping Tor while its control handshake was still in flight left that handshake retrying against nothing for fifteen seconds, and a Connect pressed meanwhile joined it and inherited its failure. A stop now ends any handshake in progress at once, and a connect that joined a warm-up which died underneath it starts its own instead of reporting someone else's error.
- **Standby comes back after a failure or a plain disconnect.** When the cold path had to be used — or a failure tore Tor down — nothing was reloaded afterwards, so the next Connect, including the automatic one fifteen seconds later, spawned Tor from scratch. Tor is warmed again two seconds after either, and a warm-up that Connect joined and went live with no longer overwrites the live state with "ready".
- **Fewer probes on a shared first hop.** Snowflake and meek carry every circuit through one volunteer proxy or one CDN front, so four warm-up probes there competed with the first page load for the link that is already the bottleneck. Those transports get two measured circuits; obfs4 and direct keep the configured number.
- **The control-silence limit is twelve seconds again.** The planner was still passing the old six-second value under the watchdog's relaxed default, so a main thread busy for six seconds could read as a dead Tor and abort a working attempt.

### New in 0.7.0 — warm start, measured circuits, a Security section, a dashboard that diagnoses

**Connecting is now one command, not a rebuild.** Veil keeps a single `tor` process loaded but held
offline — `DisableNetwork 1` and no SOCKS listener, which is observationally identical to Tor not
running — so pressing Connect no longer pays for a process spawn, a control handshake and a reload of
the consensus and relay descriptors. Which transport to try first comes from Tor's own `state` file
(the guards it actually confirmed on this machine) and from what has worked on *this* network before,
rather than from a four-second probe placed in front of everything; that probe now runs alongside the
attempt and only reorders what is left. Each attempt is supervised per stage from the events Tor
pushes, so a doomed one dies in seconds instead of burning a flat stall budget — while a slow but
working one is protected by four escapes (bytes arriving, a circuit event, a relay connection
succeeding, and a floor under every stall). Cancelling, disconnecting and switching transport now cost
one command rather than up to nine seconds of shutdown, and `AvoidDiskWrites` is gone so the guard
selection Tor learned actually survives to the next run. Fast connect has three settings: off,
standby (the default), and connect at launch — the last one is labelled plainly, because it puts Tor
traffic on the wire before you asked for it.

**Latency during a session, without touching anything already open.** Veil holds several measured
circuits open at once. Each is a stable SOCKS username/password pair, and Tor's `IsolateSOCKSAuth`
guarantees two streams with different pairs never share a circuit — so four pairs held open *are*
four parallel circuits, with no control-port commands at all. Every circuit is probed continuously
against the same target, and each new connection is sent down one of the fast ones, picked at random
among those within 25 % of the best so a single circuit never congests. Sites are pinned to their
circuit, so an exit IP does not change under a logged-in session. A connection still slow after about
a second is quietly raced on a second circuit; the threshold has a floor, so the common case is never
touched. Replacing a circuit is a key change: it cannot reach a socket that is already open, which is
why a download in flight never notices. The old exit pinning is off by default now — it collapsed
every circuit onto the same two relays, which is both slower under load and a stable pseudonym.

**Security is now its own section.** One screen answers "how protected am I right now?", scoring six
adversaries — someone on your network, your provider, the exit relay, traffic analysis, software on
this Mac, someone with this Mac — each capped by what a userspace proxy can structurally reach. The
score therefore cannot reach 100, and the screen says why. Every finding names what it costs and, where
there is an honest fix, offers one button; the entry-guard row deliberately offers none, because
clearing it would be worse for anonymity, not better. Three presets show the score they would produce
before you commit. A self-test proves the claims instead of asserting them: it opens two circuits with
different isolation keys, resolves a name through Tor rather than on this Mac, and reads back what
macOS actually has configured. Every protective control now has exactly one home here, multihop included:
pinning the middle relay's country and the timed route rotation sit next to the kill switch rather
than on the map, because they are protective choices and not place pickers — the Route screen keeps
the map and the country pickers. New controls: cutting connections that are already open when the
kill switch engages, blocking plain HTTP through Tor, deferring the update check until Tor is up,
redacting addresses from exported diagnostics, and choosing what is forgotten when Veil quits.
Country exclusions are no longer silently ignored when multihop is off.

**Home is a ledger, not a diagram.** The floating waves and running dots are gone. In their place are
twelve named stages of the path a request takes — network, Tor reachable, guard link, bootstrap,
circuit, measured circuits, exit verified, system proxy, local proxy, throughput, latency, direct
routing — each judged against thresholds that live in one file. Exactly one row is marked at a time:
the bottleneck, chosen by severity and then by chain order, because a downstream number is meaningless
when an upstream stage is broken. A failed exit verification outranks everything, since "this is not
going through Tor" is not a slowdown. One sentence at the top states the verdict, a detail pane shows
the facts behind the selected row and the actions that address it, and every value that is older than
its own refresh interval says so. Idle is rendered as idle rather than as motion: at zero bytes per
second the old animation still glided a comet. The whole screen ticks once a second on data, not
twenty-four times a second on a clock.

### Fixed in 0.6.1 — honest latency, quick wake
- **Latency no longer jumps at random.** The figure used to be the wall time of a full HTTPS fetch from check.torproject.org — a TLS handshake plus a slow, busy server, sampled once. One bad moment became "the" latency. Veil now measures the route itself: a SOCKS5 CONNECT through Tor to an anycast address, timed alone, three samples every 25 seconds against one target at a time, and the tile shows the **median of the last twelve**. Spikes appear as a jitter figure next to it instead of replacing the number, and the exit check goes back to being only an exit check.
- **Waking up is quick again.** A long sleep no longer restarts Tor by itself: Veil opens one real stream through the tunnel, and if traffic flows nothing is touched at all. Only a tunnel that actually fails is restarted. The network check that the wake path just ran is reused by the connection attempt instead of being repeated (that duplicate alone cost up to half a minute), the Wi-Fi reset will not fire twice within 90 seconds, and each transport now gets a bounded budget — a transport that worked last time gets a short leash (70 s, 28 s without progress) rather than two minutes, with an overall four-minute ceiling on the whole attempt.
- **Nothing can hang silently.** Every control-port command has a deadline; a control connection that stays silent is reported and closed instead of stranding the app. Shutting Tor down waits at most three seconds for it. The connecting panel shows how long the attempt has been running.

### New in 0.6.0 — faster routes, seamless multihop
- **Circuit races** — after connecting and after every route change Veil asks Tor for four extra circuits within your chosen countries, times how fast each one comes up (a circuit that builds fast runs through relays that answer fast), and pins the two quickest exits — and the quickest middle relay when you chose its country. Near-ties go to the relay with far more capacity. Relays are measured again every half hour, on "Measure again", and whenever the pinned ones stop answering (then Tor picks relays on its own again). The Route screen shows the pinned relays with their build times and the latency before → after; the dashboard latency tile shows the same.
- **Seamless route switching** — changing the exit or middle country, the exclusions or a timed rotation no longer sends NEWNYM. Tor gets the new constraints, Veil pre-builds the first circuit of the new route and shows it as soon as it is up; connections already open keep their old circuits until they finish, new ones take the new route at once. Rotation and "New Identity" steer away from the previous relays so the route really moves. The old behaviour (drop everything) is a switch.

### Исправлено в 0.8.4 — фильтр по стране работает до обрезки списка, и лог стал тихим
- **Закреплённая страна выхода всё ещё ничего не находила, теперь находит.** В 0.8.3 поиск стал глубже, но форма осталась прежней: взять самые ёмкие выходы, а потом выбросить те, что вне выбранной страны. Страна, чьих узлов нет среди самых ёмких в мире, по-прежнему оставалась ни с чем — это и было *«none of the 400 widest exits sits in GB»*. Теперь страна определяется для широкого среза **до** обрезки списка: несколько сотен узлов за считаные обращения к control-порту, потому что tor отвечает на многоключевой `GETINFO` за один раз, — и фильтр выбирает самые ёмкие выходы *внутри* этой страны. Если в стране только узлы постарее, требование conflux и управления перегрузкой для неё снимается, лишь бы не остаться без выхода вовсе. А когда выхода там действительно нет, лог теперь пишет, сколько узлов tor смог разместить по географии, так что разница между «в этой стране нет выхода» и «geoip ничего не сказал» видна, а не додумывается.
- **Поток предупреждений SOCKS на этот раз убран по-настоящему.** В 0.8.3 стояла строка `WarnUnsafeSocks 0`, а tor 0.4.9 ответил *«Skipping obsolete configuration option»* — опцию убрали, и предупреждения продолжались на каждом замере. Теперь замеры запрашивают `one.one.one.one`, `dns.google` и `dns.quad9.net` по имени, а не по адресу, и предупреждать tor уже не о чем. Имя стоит одного резолва на выходе при первом замере по цепочке, дальше отвечает кэш самого выхода, а разогревочная выборка, которая за это платит, отбрасывается до ранжирования полосы.

### Исправлено в 0.8.3 — страна выхода больше не обнуляет Turbo, и четыре правки по логу
- **Закреплённая страна выхода оставляла Turbo без работы.** Veil искал выход для видео среди двух десятков самых ёмких выходов мира и затем оставлял только те, что в выбранной стране. Достаточно выбрать страну, которой нет в этой мировой верхушке, — а это большинство стран, — и ответ всегда был *«none of the widest exits fits the route's country rules»*: выход не закреплён, а значит нет ни веера по цепочкам, ни гонки полос, ни замеров. Теперь поиск идёт по всему ранжированному списку, пока не наберёт достаточно кандидатов внутри выбранной страны, и сообщает, сколько выходов просмотрел, если там и правда ни одного нет. Страна узла читается из адреса, который уже есть в консенсусе, — один локальный поиск вместо двух обращений к control-порту, поэтому более глубокий поиск не стоит ни одного сетевого запроса.
- **Conflux выключен за Snowflake и meek.** Conflux нужен, чтобы дать потоку вторую ногу до выхода; за прокси-волонтёром или CDN-фронтом обе ноги идут по одному и тому же единственному звену, то есть второго пути нет вообще — есть только вдвое больше цепочек, которые надо построить через то самое узкое место, откуда и брались строки *«Our circuit … died due to an invalid selected path, purpose Unlinked conflux circuit»*. Для прямого подключения, obfs4 и своих мостов conflux остаётся.
- **Тонус больше не отнимает канал у видео за мостом.** Snowflake или meek часто дают всего несколько сотен КБ/с суммарно, а тонус на 512 КБ/с забирал их целиком: поток падал раз за разом, пока браузер ждал. За этими транспортами он теперь идёт на 128 КБ/с — достаточно, чтобы звено не уходило в slow start, и достаточно мало, чтобы видео осталась своя доля. На остальных транспортах скорость остаётся той, что вы задали.
- **Поток предупреждений SOCKS прекратился.** Замеры задержки в Veil ходят на 1.1.1.1, 8.8.8.8 и 9.9.9.9 по адресу намеренно: это константы в исходниках, ничего никогда не резолвится, а имя добавило бы DNS-запрос на выходе внутрь того самого числа, которое замер и измеряет. Tor не может отличить это от приложения, которое слило запрос, и предупреждал на каждом замере — десятки строк в минуту, погребая под собой всё остальное. `WarnUnsafeSocks` теперь выключен.

### Исправлено в 0.8.2 — исключённые страны больше не отвергают все мосты
- **Туннель, который за мостом не мог подняться в принципе.** При любом исключении стран — «Никогда не маршрутизировать через» или «Избегать стран Five Eyes» — Veil отдавал список в tor как `ExcludeNodes`, а tor сверяет его ещё и с самими мостами. Каждый мост, попавший в исключённую страну, отвергался, по строке на мост в журнале: *Not using bridge at […]: it is in ExcludeNodes.* На Snowflake, obfs4 или наборе мостов от Tor Project это означало, что отвергнуты все мосты и подключение не поднимается вообще. Ошибка была с 0.7.0, когда исключения перестали зависеть от multihop.
- **Теперь исключение действует там, где и был смысл выбора.** За мостом список уходит в `ExcludeExitNodes`: выход — то место, откуда трафик реально выходит наружу, — по-прежнему никогда не в исключённой стране, а мост, тот самый узел, который вы выбрали вручную, не трогается. Прямое подключение работает как прежде и исключает все хопы. При переходе между ними вторая форма очищается, поэтому устаревший `ExcludeNodes` не может остаться и снова отвергнуть мосты. Журнал подключения говорит об этом один раз, и экран «Локации» — под переключателем.

### Новое в 0.8.1 — одно видео, много цепочек
- **Видео идёт сразу по всем цепочкам.** YouTube привязывает медиа к адресу, с которого была загружена страница, поэтому все соединения видео обязаны выходить через один выход — из-за чего до сих пор всё семейство YouTube делило одну цепочку, и 4K упирался в пропускную способность этой одной цепочки через Tor. Но выход закреплён через `MapAddress`, а закреплённый выход — это один и тот же узел, один и тот же IP, на *любой* цепочке. Поэтому Veil теперь распределяет CDN видео (`googlevideo.com`) по всем полосам пула: четыре цепочки, четыре разных средних узла, все выходят через один закреплённый выход. YouTube по-прежнему видит один адрес; пропускная способность — это сумма. Именно это даёт логике самого плеера увидеть достаточный запас, чтобы выбрать 4K и грузить далеко наперёд, а не сбрасывать качество. Страница и API остаются на своей одной низколатентной полосе; распределяется только тяжёлое медиа. Настройки → YouTube показывают, сколько цепочек его несут.
- **Больший размер чтения для видео.** CDN видео теперь тянется из Tor кусками по 256 КБ вместо 64 КБ, так что широкая цепочка не простаивает в ожидании записи в localhost между кусками.
- Распределение включено, когда выход закреплён и пул полос работает — под Turbo 4K всегда и у всех, кто пользуется широким выходом для видео. Оно выключено при изоляции по сайтам, где каждый сайт держит одну цепочку по выбору, и когда никакой выход не закреплён, потому что тогда цепочки выходили бы через разные адреса и медиа сломалось бы.

### Новое в 0.8.0 — Turbo 4K, измерено хоп за хопом
- **Полоса для видео выбирается гонкой.** Когда выход закреплён, каждая полоса пула выходит через один и тот же выход, и единственная разница между ними — средний узел, тот хоп, который никто не выбирал. Теперь Veil тянет публичный файл через каждую полосу по три секунды и привязывает YouTube к самой широкой; цепочка, которую построил замер, и есть та цепочка, по которой затем идёт видео. Гонка повторяется, когда эта полоса уходит на покой, и каждые пятнадцать минут, пока ничего не играет. Плитка показывает измеренную скорость полосы и качество, которое она тянет.
- **Сторожевой узел тоже измеряется.** Под Turbo при прямом подключении три самых ёмких guard-узла замеряются по очереди — `EntryNodes` на каждый, один поток с собственными учётными данными, чтобы tor построил свежую цепочку, и доказательство из списка цепочек, что поток пошёл именно так, — через один широкий выход, общий для всех, и победитель закрепляется в одиночку. Узел, через который полминуты нет ни одной цепочки, отпускается раньше, чем это заметит браузер.
- **Путь запоминается.** Выход и сторожевой узел, которые несли видео в прошлый раз, закрепляются снова через секунды после следующего подключения, проверяются одним замером и остаются, пока несут хотя бы 60% прежнего; только тогда гонка запускается заново. За измерения платит первое подключение с Turbo; следующие начинают там, где оно закончило.
- **Только современные узлы.** Выход или guard для видео обязан заявлять conflux (`Conflux=1`) и управление перегрузкой (`FlowCtrl=2`), оба из tor 0.4.8: без первого нет второй ноги, без второго поток упирается в фиксированное окно за один круг, какой бы ширины ни был узел. Выходы должны также пропускать порт 80, которым пользуется поток замера.
- **Выход, который отвергает CDN видео, отбрасывается.** Плеер, который не грузит вперёд и зависает, — часто не узкий путь, а выход, которому отказывает Google: каждый запрос отвечен парой сотен байт, соединение за соединением. Мост теперь видит эту картину — несколько соединений с CDN видео через Tor за минуту закрываются почти пустыми и ни одно не несёт видео — и Veil сразу переключается на другой выход, запоминая отвергнутый на неделю.
- **Тонус идёт по собственной цепочке.** Собственные учётные данные на порту Tor, чтобы tor его изолировал. Звено, ради которого он существует, — то, которое делят все цепочки: TCP-соединение с guard или мостом, — и оно греется от любой цепочки; езда по цепочке самого видео, как было раньше, лишь отнимала 4 Мбит/с у доли видео и у каждого замера.
- **Замеры под Turbo длиннее:** пять секунд и до 25 МБ на кандидата, пять кандидатов на выход вместо трёх, чтобы широкий путь замерялся уже после разгона. Turbo также ставит четыре прокси Snowflake сразу (со следующего подключения) и выключает изоляцию по сайтам, потому что гонка полос идёт по полосам пула; и то и другое возвращается при выключении Turbo. Пресет безопасности, закрепляющий изоляцию, теперь выключает Turbo и говорит об этом.

### Новое в 0.7.11 — Turbo 4K: одна кнопка, всё через Tor
- **Turbo 4K.** Один переключатель — на плитке YouTube, в Настройки → YouTube, в окне строки меню, в меню приложения (⇧⌘4) и как Быстрая команда — для всего, что делает YouTube быстрым через Tor, и ничего мимо Tor: YouTube через Tor, самый ёмкий измеренный выход для всех хостов YouTube, самый ёмкий сторожевой узел (режим 8K), канал в тонусе на 512 КБ/с и выше всё время, пока туннель поднят, conflux в режиме пропускной способности, маскировка трафика, multihop и закрепление узлов выключены, а цепочки принимают новые потоки полчаса вместо десяти минут (`MaxCircuitDirtiness`), и измеряемые полосы живут двадцать пять минут под стать — видео это одна долгая сессия, а каждый переезд на свежую цепочку это холодный старт. Нажатие при подключении сразу заставляет путь видео доказать себя заново; плитка затем показывает измеренную скорость и качество, которое она тянет.
- **Выключить — значит вернуть, а не сбросить.** Turbo помнит, что менял, и при выключении возвращает каждую настройку как было. Изменение любой из управляемых им настроек вручную выключает Turbo и возвращает остальные, так что переключатель всегда говорит то, что реально работает. Пресет безопасности ложится поверх Turbo, если не ставит ничего наоборот; тот, что ставит («Приватность прежде всего» с маскировкой, «Скорость прежде всего» с YouTube мимо Tor), выключает его и пишет об этом в журнал.
- **Чего он не может — сказано там, где нажимают.** За Snowflake или meek потолок — мост, и никакой режим его не поднимет; плитка говорит об этом и называет, что нужно для 4K: прямое подключение или obfs4. Сторожевой узел, выбранный по ёмкости, остаётся замечанием на экране «Безопасность», и его исправление одним нажатием выключает Turbo.

### Изменено в 0.7.10 — канал в тонусе, как просили
- **512 КБ/с всё время, пока туннель поднят, одним непрерывным потоком.** В 0.7.9 цепочка видео грелась на 128 КБ/с, только пока шло видео, и серией маленьких запросов — то есть серией пауз. Как просили: теперь поток идёт на 512 КБ/с по умолчанию (на выбор 128, 256 и 1024) всё время, пока туннель поднят, и это одна непрерывная загрузка большого публичного файла, читаемая фиксированными кусками десять раз в секунду — окно приёма держит отправителя ровно на этой скорости, без пауз запрос/ответ вообще. Когда файл кончается, следующий начинается сразу; когда источник отказывает, берётся следующий. По цепочке самого видео, пока открыто соединение с YouTube, иначе по основному маршруту, который делит звено guard или моста со всем остальным. «Только пока идёт видео» остаётся выбором.
- **На просадку — действие, а не наблюдение.** Поток и есть измеритель: как только он достиг половины цели, четверть цели, продержавшаяся полминуты, — или полная остановка потока — означает, что путь под ним просел. Тогда цепочки заменяются, чтобы новые соединения получили свежие, задержка маршрута измеряется заново, а выход для видео обязан доказать себя снова; не чаще раза в три минуты. Поток никогда не сдаётся, пока он нужен: возвращение пути — ровно тот момент, когда он должен быть на месте.

### Новое в 0.7.9 — цепочка видео в тонусе
- **Ровный небольшой поток по цепочке видео, пока идёт видео.** Плеер забирает порцию, ждёт, пока буфер опустеет, забирает снова; в паузах TCP-соединение на каждом хопе простаивает, и Linux-узлы сжимают окно перегрузки после простоя длиннее одного круга. Каждая порция затем разгоняется с маленького окна заново — та самая «пила» на графике скорости и подвисание, когда порция не успевает разогнаться раньше, чем опустеет буфер. Пока через Tor открыто соединение с YouTube, Veil держит по той же цепочке небольшой ровный поток — маленькие запросы к CDN картинок YouTube несколько раз в секунду, с учётными данными той же полосы, так что они делят её цепочку и выход, — и окно на каждом хопе остаётся полным. Настройки → YouTube: включено по умолчанию на 128 КБ/с, на выбор 64, 256 и 512; подпись объясняет, чего стоит скорость. Поток останавливается, как только закрывается последнее соединение с YouTube, и следует за полосой, на которой браузер оказался после замены.

### Новое в 0.7.8 — путь видео измерен; режим 8K; две плитки, которые что-то говорят
- **Выход для видео выбирается по тому, что он реально несёт, а не по заявленному весу.** После подключения Veil тянет публичный файл через собственный выход Tor и через каждый из трёх самых ёмких выходов по очереди, по четыре секунды, и закрепляет YouTube за самым быстрым — только если он обгоняет собственный выход Tor. Скорость видна в Настройки → YouTube рядом с качеством, которое она тянет (1080p от 5 Мбит/с, 4K от 22, 8K от 50), а кнопка **«Измерить путь видео»** повторяет замер по требованию. За Snowflake или meek ничего не измеряется: потолок — мост, выход только проверяется. Привязка, которая у YouTube уже есть, сохраняется на время замера кандидатов, так что играющее видео никуда не переезжает.
- **Режим 8K** (Настройки → YouTube, по умолчанию выключен). При прямом подключении сторожевой узел — второй край потолка. С этим режимом Veil ограничивает сторожевой узел Tor тремя самыми ёмкими guard-узлами консенсуса и оставляет ограничение, только когда цепочка через один из них действительно построена. Это касается всех сайтов, не только YouTube, и экран «Безопасность» учитывает это как замечание: узел, выбранный по ёмкости, — маленький предсказуемый набор, общий для всех пользователей режима. Мосты сохраняют свой первый хоп, так что за Snowflake, obfs4 или meek режим ничего не делает и говорит об этом. Чего не может ни один режим: заставить одну цепочку Tor нести больше, чем дают guard, middle и exit. 8K нужно около 50 Мбит/с; замер показывает, есть ли они у пути.
- **Плитка задержки снова работает.** При включённых измеряемых цепочках — по умолчанию с 0.7.0 — монитор задержки маршрута вообще не запускался, и плитка вечно показывала «Измеряем…». Теперь он работает вместе с пулом.
- **Плитка маскировки трафика говорит, что маскировка делает:** скорость покрывающего трафика, его доля от всего на проводе, байты, отправленные и полученные через onion-петлю, и одна строка о том, что скрывает выбранный уровень, — вместо названия уровня и одного числа под волной.

### Новое в 0.7.7 — смена сети замечается, перезапуск не виден, мосты, когда ничто другое не работает
- **Замечается смена сети, а не только её потеря.** macOS сообщает о потере и восстановлении пути, но переход с Wi-Fi на Ethernet, с одной сети на другую, появление или исчезновение VPN часто оставляют путь «удовлетворённым» всё время — тогда как соединение со сторожевым узлом уже мертво, и каждый запрос висит, пока что-нибудь другое это не заметит. Теперь Veil следит за интерфейсами и шлюзами, по которым идёт путь: если они меняются под живым туннелем, туннель сразу проверяется и перезапускается только при неудаче; если меняются после сбоя, следующая попытка идёт через три секунды, а не по истечении паузы.
- **Перезапуск удерживает запросы, а не отклоняет их.** Во время мягкого реконнекта — после пробуждения, смены сети, сбоя маршрута — новые соединения раньше отклонялись, и страница, запрошенная в эти секунды, показывала ошибку. Теперь они удерживаются — никуда не направляются и не получают ответа (ничего не утекает) — и пропускаются, когда туннель вернулся: страница загружается на несколько секунд позже. То же удержание покрывает первые секунды после пробуждения, пока туннель проверяется. Удержание само заканчивается через полминуты.
- **Мосты от Tor Project, когда все транспорты отказали.** В сети, которая жива, но блокирует Snowflake, встроенные мосты obfs4 и meek, автоматический транспорт раньше сдавался. Теперь он делает то же, что помощник подключения Tor Browser: запрашивает у bridges.torproject.org — напрямую, затем через CDN с domain fronting — мосты obfs4 и webtunnel, рекомендованные для этой страны, тут же пробует их и сохраняет, чтобы следующее подключение в этой сети начиналось с них. Они видны в Настройки → Мосты с кнопкой «Забыть»; собственные строки мостов пользователя всегда имеют приоритет.
- **Автопереподключение делает паузы, а не долбит.** Последовательные сбои ждут 15, 30, 60, 120, 240 секунд и затем пять минут между попытками; успех, восстановленный путь или смена сети сбрасывают счёт. Без сетевого пути вообще ничего не повторяется — возвращение пути само назначает попытку.

### Исправлено в 0.7.6 — меньше перезапусков, бюджеты по часам
- **Дрожание сети больше не рвёт рабочий туннель.** Если путь пропадал и возвращался при подключённом туннеле, безусловно планировался полный реконнект — все цепочки сбрасывались из-за икоты Wi-Fi или мигания интерфейса, которые ничего не стоили. Теперь одна проба после стабилизации пути решает, и перезапускается только туннель, который действительно не работает.
- **Бюджеты идут по часам, а не по моменту прогрева.** Standby может простоять часы; консенсус, свежий при запуске, живёт ограниченное время, и бюджеты стадий, выставленные по старой свежести, оказывались слишком тесными для загрузки каталога, которую следующему подключению предстояло сделать — ложное «зависание» на первом подключении за день. Свежесть теперь перечитывается по часам в момент подключения.
- **Жёсткий таймаут щадит попытку, которая ещё движется.** Загрузка каталога через медленный мост могла пережить бюджет, пока байты ещё шли. Теперь за пределами бюджета попытка обрывается, только если ещё и двадцать секунд не было прогресса, либо прошло вдвое больше бюджета.
- **Порты, выбранные часы назад, перепроверяются перед использованием.** SOCKS-, HTTP- и порт полос выбираются при старте standby; кто угодно на Mac может занять один из них, и занятый порт полос раньше ронял всё подключение. Каждый ещё не занятый порт проверяется и перевыбирается прямо перед использованием; слушатель, не сумевший привязаться при активации, тоже перевыбирается.
- **«Подключаемся» считается запуском.** На медленном диске разбор консенсуса мог задержать холодный путь дольше срока запуска, ещё до первой попытки соединения с узлом; собственное «подключаемся к узлу» от tor теперь этот срок закрывает, а срок для прямого подключения вырос на две секунды.
- **Первое соединение с сайтом получает 25 секунд вместо 10.** Постройка цепочки, разрешение имени на выходе и медленный сервер подряд могли превысить старый срок моста, и браузер показывал ошибку для страницы, которая загрузилась бы. Onion-сервисы получают 45.

### Новое в 0.7.5 — браузер, который выдаёт меньше
- **Защищённое окно браузера** (Безопасность → Управление). То, что сайт видит внутри HTTPS — браузер и его версию, операционную систему, языки, ваш адрес глазами WebRTC, — выдаёт браузер; прокси не может залезть в зашифрованное соединение и это изменить, поэтому сайт проверки IP по-прежнему называет ваш Mac и ваш Chrome за выходным узлом Tor. Теперь Veil открывает уже установленные браузеры так, как устроен Tor Browser: отдельный профиль, который ходит только через Veil, WebRTC вдали от настоящего адреса, QUIC выключен, личность обобщённая — Firefox через собственную защиту от снятия отпечатка (`privacy.resistFingerprinting`: Firefox под Windows, часы в UTC, стандартный экран, без WebGL), браузеры на Chromium (Brave, Chrome, Edge, Vivaldi, Chromium) — через фиксированный user agent под Windows без client hints. Обычный профиль не затрагивается. Адрес по-прежнему выходной узел Tor, и любой сайт это определит: это Tor работает, а не утечка.

### Новое в 0.7.4 — YouTube через Tor, широко
- **Один поток — две цепочки.** Conflux выключался всякий раз, когда был выключен его режим задержки. Теперь он включён всегда и по умолчанию в режиме пропускной способности: Tor строит два плеча до выходного узла, и выход раскладывает один поток на оба — единственный способ, которым одно TLS-соединение, например видеоплеера, получает больше доли одной цепочки. Режим задержки остался переключателем в Настройки → Маршрут.
- **Широкий выход для видео.** Случайный выход — это случайная доля случайного канала. При YouTube через Tor Veil после подключения читает консенсус, берёт выходы с наибольшей измеренной ёмкостью, подходящие под правила стран маршрута, и привязывает все хосты YouTube к первому, который реально проводит туда поток (`MapAddress … .exit`, по назначению — без глобального `ExitNodes`, без влияния на другие сайты). Выход перепроверяется каждые пятнадцать минут и заменяется, если перестал отвечать. В Настройки → YouTube видно, какой это узел; там же переключатель.
- **Вся сессия YouTube выходит через один выход.** YouTube привязывает адреса медиа к IP, с которого загружена страница, поэтому плеер на youtube.com и видео на googlevideo.com должны делить один выход — а с измеряемой цепочкой на каждый сайт не делили. Семейство хостов YouTube теперь один сайт для пула цепочек, как это делает изоляция по первой стороне в Tor Browser.
- YouTube по умолчанию остаётся через Tor; прямой путь с обходом замедления — выбор в Настройки → YouTube, и сделанный там выбор теперь запоминается как выбор.

### Исправлено в 0.7.3 — проба советует, узел решает
- **Цензурируемой сети больше не сбрасывают Wi-Fi за то, что она работает.** Проба связности стучится к публичным резолверам и паре известных хостов; сеть, которая их блокирует, всё равно может нести Snowflake, чьё рандеву длится дольше пробы. Вердикт «нет интернета» раньше обрывал попытку на месте и затем сбрасывал Wi-Fi. Теперь он лишь укорачивает поводок — шесть секунд, чтобы узел ответил, — а ответивший узел или пришедшие байты отменяют его: ни обрыва, ни сброса Wi-Fi. Сброс по-прежнему срабатывает там, где нужен: на попытке, которая не достучалась ни до чего.
- **Ответ узла считается прогрессом.** После удержания сети проценты стоят на месте, пока tor разговаривает со сторожевым узлом; теперь этот разговор — прогресс для сторожа попытки, и медленный узел больше не принимается за зависание.
- **После пробуждения туннель проверяется повторно, когда Wi-Fi уже вернулся.** Первая проверка после сна идёт, пока Wi-Fi ещё переподключается, и падает только поэтому. Как только ремонт сети сообщает, что интернет есть, туннель спрашивается ещё раз — и соединение со сторожевым узлом, пережившее короткий сон, остаётся нетронутым вместо перезапуска.
- **Tor, ещё не отпустивший блокировку каталога данных, больше не срывает запуск.** Холодный путь ждёт, пока убитый процесс действительно исчезнет, и один раз повторяет запуск секундой позже, если блокировка ещё держится.

- **Главная — снова схема маршрута и плитки.** Ступенчатый список из двенадцати стадий, появившийся в 0.7.0, убран; дашборд — это опять кнопка питания со статусом и «чипами», живой маршрут (Mac → мост → узлы → интернет) и плитки скорости, сессии, задержки, защиты, маскировки, маршрутизации, YouTube, приложений и сети. ### Исправлено в 0.7.1 — «подключено» только когда цепочка действительно есть
- **Больше нет «подключено» без маршрута.** После удержания сети — а так заканчивается каждое отключение, каждый неудавшийся транспорт и каждый мягкий реконнект: Tor остаётся загруженным, но офлайн — счётчик bootstrap и флаг `status/circuit-established` остаются на своём максимуме и говорят «готово» до того, как построена хоть одна цепочка. Второе подключение за сессию могло через три секунды стать зелёным без маршрута под ним, а первая страница — зависнуть. Теперь «готово» от повторно активированного Tor принимается только после реально построенной цепочки (событие `CIRC … BUILT` либо открытая цепочка в `circuit-status`, где перечислены только живые), первый опрос идёт через секунду после активации вместо трёх, а завершение цепочки сдвигает опрос вперёд.
- **Отключение, совпавшее со стартовым standby, больше не ломает следующее подключение.** Остановка Tor в момент, когда рукопожатие управляющего порта ещё шло, оставляла его пятнадцать секунд стучаться в пустоту, а нажатое тем временем «Подключить» присоединялось к нему и наследовало его ошибку. Теперь остановка сразу завершает любое идущее рукопожатие, а подключение, присоединившееся к погибшему прогреву, запускает свой вместо чужой ошибки.
- **Standby возвращается после сбоя и после обычного отключения.** Если пришлось идти холодным путём или сбой снёс Tor, дальше ничего не перезагружалось — и следующее подключение, включая автоматическое через пятнадцать секунд, запускало Tor с нуля. Теперь Tor прогревается снова через две секунды в обоих случаях, а прогрев, к которому присоединилось подключение и ушло в работу, больше не перезаписывает живое состояние словом «готов».
- **Меньше проб на общем первом хопе.** Snowflake и meek пропускают все цепочки через один волонтёрский прокси или один CDN-фронт, и четыре разогревающие пробы там конкурировали с первой страницей за канал, который и так узкое место. Эти транспорты получают две измеряемые цепочки; obfs4 и прямое подключение — сколько настроено.
- **Лимит тишины управляющего порта снова двенадцать секунд.** Планировщик всё ещё передавал старые шесть секунд поверх смягчённого значения сторожа, и занятый шесть секунд главный поток мог выглядеть как мёртвый Tor и оборвать рабочую попытку.

### Исправлено в 0.6.1 — честная задержка, быстрое пробуждение
- **Задержка больше не скачет случайно.** Раньше это было время полной загрузки страницы с check.torproject.org: TLS-рукопожатие плюс медленный загруженный сервер, и всего один замер. Одна неудачная секунда становилась «той самой» задержкой. Теперь Veil измеряет сам маршрут: SOCKS5-подключение через Tor к anycast-адресу, замеряется только оно, три пробы каждые 25 секунд к одной цели, а плитка показывает **медиану последних двенадцати**. Всплески отображаются рядом как джиттер, а не подменяют число; проверка выхода снова только проверяет выход.
- **Пробуждение снова быстрое.** Долгий сон больше сам по себе не перезапускает Tor: Veil открывает один настоящий поток через туннель, и если трафик идёт — ничего не трогается. Перезапуск только если туннель действительно не работает. Проверка сети, только что выполненная при пробуждении, переиспользуется попыткой подключения, а не повторяется (один этот дубль стоил до полуминуты), сброс Wi-Fi не срабатывает дважды за 90 секунд, а каждому транспорту теперь отведён ограниченный бюджет: сработавший в прошлый раз получает короткий поводок (70 с, 28 с без прогресса) вместо двух минут, и вся попытка ограничена четырьмя минутами.
- **Ничто не зависает молча.** У каждой команды управляющего порта есть срок; молчащее управляющее соединение закрывается с сообщением, а не подвешивает приложение. Остановка Tor ждёт его не дольше трёх секунд. На панели подключения виден таймер попытки.

### Новое в 0.6.0 — быстрее маршрут, бесшовный multihop
- **Гонка цепочек** — после подключения и после каждой смены маршрута Veil просит Tor построить четыре дополнительные цепочки в выбранных странах, измеряет, как быстро каждая поднимается (быстро собирающаяся цепочка идёт через быстро отвечающие узлы), и закрепляет два самых быстрых выходных узла, а при выбранной стране промежуточного узла и самый быстрый промежуточный. При почти равном времени предпочтение узлу с заметно большей пропускной способностью. Узлы измеряются заново каждые полчаса, по кнопке «Измерить снова» и когда закреплённые перестают отвечать (тогда Tor снова выбирает узлы сам). На экране «Маршрут» видны закреплённые узлы с временем сборки и задержка до → после; плитка задержки на дашборде показывает то же.
- **Бесшовное переключение маршрута** — смена выходной или промежуточной страны, исключений и ротация по таймеру больше не шлют NEWNYM. Tor получает новые ограничения, Veil заранее строит первую цепочку нового маршрута и показывает её, как только она готова; открытые соединения остаются на старых цепочках, пока не завершатся, новые сразу идут по новому маршруту. Ротация и «Новая личность» уводят от прежних узлов, чтобы маршрут действительно менялся. Старое поведение (сбросить всё) осталось переключателем.
- **Conflux в режиме задержки** — Tor строит два плеча до выходного узла и теперь отправляет данные по плечу с меньшей задержкой (`ConfluxClientUX latency`), а не по более широкому.
- **Несколько Snowflake-прокси одновременно** — клиент Snowflake держит два волонтёрских прокси (настраивается 1–4), чтобы медленный не тормозил сессию.

### Новое в 0.5.0
- **Сеть, которая «есть», но не работает** — после сна или после отключения другого VPN macOS показывает рабочую сеть, но ничего не проходит, пока не выключить и включить Wi-Fi. Теперь Veil проверяет интернет (TCP к публичным резолверам плюс DNS-запрос) перед запуском Tor и после каждого пробуждения; если проверка не проходит, сам выключает и включает Wi-Fi (CoreWLAN, затем `networksetup`, затем перезапуск сетевой службы через SystemConfiguration), ждёт сеть и только потом запускает Tor. Транспорт, зависший на «рабочей» сети, один раз вызывает тот же сброс и пробуется снова. После долгого сна Tor перезапускается целиком, Tor больше не уходит в спящий режим, а «Сбросить сеть» (⇧⌘R) есть в меню, строке меню, на дашборде и в Настройках → Сеть.
- **Дашборд** — главный экран стал живой интерактивной панелью: анимированный маршрут (Mac → мост → узлы → интернет), где частицы движутся со скоростью реальной загрузки/отдачи/маскировки, узлы загораются по мере загрузки Tor, наведение показывает детали, а клик ведёт на нужный экран; красная «быстрая полоса» показывает YouTube в обход Tor; kill switch нарисован как барьер. Плитки: скорость (живой спарклайн), сессия (новая личность по клику), задержка маршрута (проверка Tor по клику), защита, маскировка трафика (эквалайзер и переключатель), маршрутизация, скорость YouTube, приложения и состояние сети.
- **Telegram** — приложение Telegram игнорирует системный прокси и не замечает Tor. Одна кнопка («Добавить прокси Veil в Telegram» на дашборде или в Настройках → Сайты) передаёт Telegram ссылку `tg://socks`, которая добавляет Veil как SOCKS5-прокси, и Telegram работает через Tor.
- **App Store, iCloud и обновления** по умолчанию идут напрямую (новый пресет «Apple» в Настройках → Сайты), потому что выходные узлы Tor их ломают; при желании переключите на Tor.
- Прямые (антизамедление) соединения и проверки доступности принудительно не используют системный прокси, поэтому не могут зациклиться на самом Veil.

### Исправлено в 0.3.1
- **Маскировка трафика** не могла достучаться до своего onion-сервиса. Теперь Veil ждёт событие Tor `HS_DESC UPLOADED` перед подключением, повторяет попытки с разумными интервалами и сам говорит с Tor по SOCKS5, поэтому `.onion`-имена (и вообще любые имена хостов) резолвит Tor, а не macOS. HTTP-мост и проверка Tor идут тем же путём — заодно исключены утечки DNS.

### Новое в 0.3.0
- **YouTube** — выбор пути для YouTube: через Tor, напрямую с обходом замедления (TLS ClientHello дробится по SNI, чтобы замедляющий DPI не прочитал имя хоста — как GoodbyeDPI/ByeDPI) или просто напрямую. Четыре техники фрагментации, список других доменов в обход Tor и встроенная проверка.
- **YouTube Turbo** — прокси с обходом замедления вообще без Tor: через Veil идёт только YouTube, остальное не трогается.

### Новое в 0.2.0
- **Маскировка трафика (в стиле DAITA)** — пустой трафик, проходящий через Tor до приватного onion-сервиса на вашем Mac, скрывает форму реального трафика от наблюдателя в локальной сети: фоновый шум, всплески в стиле FRONT при активности, режим постоянной скорости. Также принудительно включён circuit/connection padding самого Tor.
- **Многократный переход** — карточка маршрута с живой схемой (Mac → Snowflake → промежуточный → выходной → интернет), выбор страны промежуточного узла, исключение стран, пресет «Пять глаз», смена маршрута по таймеру и измеренная задержка.

### Установка
1. Откройте DMG и перетащите **Veil.app** в *Программы*.
2. Сборка подписана ad-hoc: при первом запуске откройте **Системные настройки → Конфиденциальность и безопасность → Всё равно открыть**, либо выполните `xattr -cr /Applications/Veil.app`.
3. Нажмите кнопку питания. macOS один раз спросит пароль администратора для переключения системного прокси.

Requires macOS 26 Tahoe.
