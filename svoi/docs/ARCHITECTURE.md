# Устройство svoi

Этот документ — для тех, кто хочет понять, **как** это работает без сервера-координатора, и
проверить, что заявленное действительно так. Пользовательское описание — в [../README.md](../README.md),
контракт между интерфейсом и ядром — в [UI-API.md](UI-API.md).

## Что заменяет «облако Tailscale»

В Tailscale центральный сервер делает три вещи: **(1)** знает, какие устройства входят в сеть и
кто им доверяет (ключи и права), **(2)** сообщает устройствам адреса друг друга, **(3)** помогает
пробить NAT и, если не вышло, ретранслирует (DERP). В svoi:

| Роль сервера | Как сделано здесь |
|---|---|
| Кто в сети, кому можно верить | **Корневой ключ сети** подписывает сертификат каждого устройства. Проверить участника можно офлайн. Список участников хранит и распространяет каждый участник. |
| Адреса друг друга | Адреса лежат **в приглашении**; дальше участники сами обмениваются адресами всех остальных (*peer-state*) и находят друг друга в локальной сети широковещательными маячками. |
| Пробитие NAT | Роль «встречи» исполняет любой общий участник: он пересылает короткое зашифрованное «позвони мне» (*call-me-maybe*). Внешний адрес узнаётся по STUN (необязательно) или от самих участников. |
| Ретрансляция | Любой участник с достижимым адресом (настройка «Ретранслятор») пересылает зашифрованные пакеты между двумя другими. |

Цена отказа от сервера описана в разделе «Чего здесь нет».

## 1. Личность и доверие (`internal/identity`)

* **Устройство** = пара ключей Ed25519, создаётся при первом запуске (`device.key`, `0600`).
  *ID устройства* — открытый ключ (52 символа base32). Всё остальное — метки.
* **Сеть** = корневая пара Ed25519, создаётся командой `init`. Корневой сертификат
  (самоподписанный X.509) знают все участники; **секретная часть есть только у администраторов**.
* **Участник** — X.509-сертификат, подписанный корнем: `CN` — имя устройства, `O` — владелец,
  `DNS` — `<имя>.svoi`, IP-адреса оверлея (IPv4 из `100.64.0.0/10`, IPv6 из ULA `fd…/48`, считаются
  от ключа, коллизии IPv4 разрешаются), расширение с флагом администратора (OID `2.999.7.1`).
  Сертификат участника с ключом устройства используется как обычный TLS-сертификат — на нём работает mTLS.
* **Отзыв.** Администратор подписывает запись «устройство X отозвано в момент T». Записи
  распространяются по сети вместе со списком участников; отозванный не принимается ни одним узлом.
* **Приглашение** (`SVOI1-…`, ~275 символов с адресами) содержит: корневой открытый ключ, ключ
  пригласившего, 16 байт секрета, срок, флаг «администратор», до 8 адресов пригласившего и название
  сети. Используется один раз.
* **Вступление** (`join.go`): новичок открывает QUIC (ALPN `svoi-join/1`) на адрес из приглашения,
  проверяет сертификат пригласившего по корню *из приглашения* (значит, подменить собеседника
  нельзя), и доказывает знание секрета HMAC-ом, привязанным к **этой TLS-сессии** (exporter), —
  перехваченный и пересланный запрос не сработает. В ответ приходят его сертификат, список
  участников и (для админ-приглашения) секретный ключ сети. После пяти неверных доказательств
  приглашение перестаёт приниматься. Рукопожатия вступления ограничены **по адресу отправителя**
  (адрес уже подтверждён QUIC Retry): у каждого свой небольшой бюджет, плюс общий потолок, —
  посторонний, долбящий порт, не может исчерпать бюджет того, у кого на руках приглашение.
* **Передача прав администратора** — RPC `mesh.grant`: ключ сети передаётся по уже установленному
  зашифрованному каналу. Понизить администратора нельзя (ключ уже скопирован) — это честно
  отражено в API (`unsupported`). **Отзыв администратора его не обезвреживает**: корневой ключ остаётся у
  него, и он может выпустить сертификат новому устройству. Чтобы по-настоящему исключить администратора,
  нужна новая сеть.
* **Исключение устройства.** Администратор подписывает отзыв и, пока канал ещё жив, посылает его самому
  устройству (`mesh.revoked`): оно проверяет подпись корнем, записывает «вас удалили из сети «X»», забывает
  сеть и **берёт новый ключ** (старый навсегда в списке отзыва, с ним вступить нельзя). Если устройство было
  выключено, оно просто увидит, что все «не в сети»: сообщить ему иначе нельзя — к нему никто не подключится.

Вывод для модели угроз: **компрометация администратора = компрометация сети**. Это цена отсутствия
сервера, который мог бы ограничивать права; для домашней сети из 3–10 устройств это приемлемо.

## 2. Транспорт (`internal/magic`)

`magic.Conn` — реализация `net.PacketConn`, поверх которой работает QUIC. Для QUIC каждый
участник выглядит как «виртуальный» UDP-адрес (`[fdc7:5e57::r8]:порт`, где `r8` — 8 байт хеша ключа);
а какой реальный путь использовать — решает `magic`, QUIC об этом не знает и не должен.

**Типы пакетов** (первый байт, все ≥ `0xA0`, чтобы не путаться со STUN и DHT):

| байт | назначение |
|---|---|
| `0xA1` data | `[src8][mac8][пакет QUIC]` — прямой |
| `0xA2` relay-out | `[src8][dst8][mac8][внутренний пакет]` — клиент → ретранслятор |
| `0xA3` relay-in | `[relay8][src8][mac8][внутренний пакет]` — ретранслятор → клиент |
| `0xA4` anon | пакет QUIC от того, кто ещё не участник (только для вступления) |
| `0xA5` disco | `[ключ отправителя][nonce][NaCl box]` — служебное |

**Подлинность пакетов `data`.** QUIC шифрует содержимое, но сам по себе не знает, «от кого» пришла
датаграмма: достаточно знать публичный ключ участника, чтобы подбросить стеку пакеты с его
`src8`, заставить узел зондировать чужие адреса или вытеснить настоящие адреса-кандидаты. Поэтому
каждый пакет несёт 8-байтовый MAC (BLAKE2s; отдельный ключ, выведенный из общего секрета двух
устройств с меткой `data`). В MAC входят тип пакета, **оба** `r8` (отправителя и получателя) и тело —
пакет нельзя ни отразить обратно отправителю, ни воспроизвести третьему устройству. Пакет с
неверным MAC отбрасывается до QUIC и ничему не «учит» узел; адрес, с которого пришёл *проверенный*
пакет, принимается как новый кандидат не чаще раза в секунду (участник может «переехать», но не
может засыпать нас адресами).

**Присоединяющиеся (`0xA4`).** Пакеты того, кто ещё не участник, идут прямо в QUIC, но транспорт
требует от таких источников **QUIC Retry** (подтверждение адреса отправителя): пока он не
подтверждён, у узла нет о нём никакого состояния, и узел нельзя заставить отвечать на подставной
адрес (усиление). Участникам (виртуальные адреса) Retry не нужен. Тест `anonflood_test.go` показывает
разницу: без Retry поток поддельных Initial порождает состояние на каждый пакет.

**Disco** запечатан NaCl-box между ключами двух устройств, поэтому ретранслятор не может его
прочитать или подделать, а сканер порта не получает **никакого** ответа. Ключ box одинаков в обе
стороны, поэтому внутрь запечатаны ещё и `r8` отправителя и получателя: иначе посторонний мог бы
вернуть пакет его автору, подменив отправителя в заголовке, и тот принял бы его «от собеседника».
Сообщения: `ping`/`pong`
(проверка адреса-кандидата, заодно измерение RTT; в первом пинге можно приложить сертификат),
`call-me-maybe` (просьба открыть встречное соединение: «я сейчас шлю на твои адреса — шли на мои»),
`peer-state` (мои адреса, видимые мне адреса соседей, согласен ли ретранслировать).

**Выбор пути для каждого партнёра** (`peer.go`): LAN → прямой (самый быстрый проверенный) →
через ретранслятор. Пока путь не найден, пакеты идут через ретранслятор (если он есть);
как только `pong` приходит по прямому адресу, трафик переключается на него (без разрыва QUIC —
адрес виртуальный). Живой путь поддерживается keep-alive (5 с, в простое 20 с), «протухает» через
16 с тишины.

**Откуда берутся адреса-кандидаты** (`endpoints.go`): адреса интерфейсов, внешний адрес по STUN
(`stun.l.google.com:19302`, `stun.cloudflare.com:3478`; можно отключить), адреса, под которыми
нас *видят* другие участники (observed), и адреса из последнего приглашения. `NetCheck` определяет
сложность NAT: если один и тот же локальный порт отображается на разные внешние — NAT симметричный
(`hard`), и пробить его не получится.

**Ретрансляция.** Любой участник (если ретрансляция ему разрешена в настройках), получив `relay-out`,
проверяет MAC (BLAKE2s; ключ — секрет Диффи—Хеллмана между отправителем и этим участником),
а затем пересылает внутренний пакет адресату как `relay-in` с MAC уже для следующего участка. Содержимое — зашифрованные пакеты QUIC между конечными устройствами: ретранслятор видит
размеры и тайминги, но не данные. MAC нужен, чтобы посторонний не мог использовать участника как
открытый ретранслятор для собственного трафика. Квот на ретранслируемый трафик нет — устройство,
которому это не нужно (телефон на тарифе), выключает ретрансляцию в настройках.

**Локальная сеть** (`mesh/lan.go`): раз в 5 секунд устройство рассылает маячок
(multicast `239.255.77.77` и broadcast подсети, UDP `41711`). Маячок **запечатан**
(XChaCha20-Poly1305) ключом, выведенным из корневого ключа сети, со случайным nonce при каждой
отправке: `[версия][nonce 24][seal(ключ устройства 32 | UDP-порт 2)]`. Посторонний в той же
Wi-Fi-сети видит лишь случайные байты: не узнаёт ни ключ устройства, ни сеть, не может связать
два маячка друг с другом (следить за устройством от кафе к кафе) и не может подделать маячок.
Маячок — лишь подсказка «устройство, вероятно, по этому адресу»; настоящая проверка — disco и mTLS.
Принимаются маячки только с адресов **своей подсети** (подставной источник из другой сети не может
заставить нас зондировать чужой адрес).
Благодаря этому две машины в одной Wi-Fi-сети соединяются **без интернета** и без пробития.

## 3. Узел сети (`internal/mesh`)

* **Линки.** Между каждой парой участников — одно QUIC-соединение (TLS 1.3, взаимная проверка
  по корню, ALPN `svoi/1`). Если оба стороны открыли одновременно, остаётся то, которое открыло
  устройство с меньшим ID (одинаково решается на обеих сторонах). Инициатор — устройство с меньшим ID,
  второе ждёт 6 секунд («пассивное ожидание») и только потом пробует само.
* **RPC.** Запросы идут по потокам QUIC: `[длина][JSON]`, при необходимости за заголовком следует
  «сырое» тело (так передаются файлы без Base64 и без загрузки в память). Для TUN используются
  QUIC-датаграммы. Коды ошибок: `denied`, `notfound`, `invalid`, `exists`, `offline`, `busy`,
  `toolarge`, `unsupported`, `internal`.
* **Синхронизация** (`mesh.sync`): участники обмениваются сертификатами и отзывами (всё подписано
  корнем, поэтому доверять посреднику не нужно: принимается только то, что проверяется корнем) и
  свежим «hello» (ОС, версия, возможности, опубликованные сервисы). Новый участник, добавленный на
  одном устройстве, становится известен всем остальным без участия «центра».
* **События** (`Subscribe`) — для интерфейса: изменение списка, пути, имени.

## 4. Приложения

**Файлы** (`internal/files`). *Общая папка* — корневой каталог, открываемый через `os.Root`
(ядро запрещает выход за его пределы: `..`, абсолютные ссылки, симлинки наружу). Режим `ro`/`rw`,
список разрешённых устройств. Удалённый просмотр, чтение с `Range` (видео и музыка перематываются),
загрузка, переименование, удаление, миниатюры (с учётом EXIF-ориентации). Открываются только обычные
файлы и папки: именованный канал (FIFO) внутри папки не может повесить обработчик (открытие
неблокирующее, не-обычный файл отклоняется), а список папки читается не больше лимита записей.
*Передача* — по принципу «забирает получатель»: отправитель публикует предложение (`xfer.offer`) и
держит файл; получатель (вручную или по политике автоприёма `own`/`all`/`ask` и лимиту) скачивает
сам, с докачкой после обрыва. Поэтому отправка «на выключенный телефон» просто ждёт, когда
он появится.

**Почта и чат** (`internal/mail`). Сообщение подписывается ключом устройства-отправителя, хранится в
его исходящих и доставляется получателю (`mail.deliver`) с подтверждением и повторами. Доставка
идемпотентна (дедупликация по ID), так что потеря подтверждения не создаёт дубликатов. Вложения —
блобы, адресуемые по SHA-256 (`internal/blob`): получатель скачивает их у отправителя и проверяет
хеш. Блоб отдаётся только **автору и адресатам** сообщения, которое его несёт (хеш — не ключ к
файлу), а на запрос постороннего ответ тот же, что и для несуществующего блоба, — по нему нельзя
выяснить, есть ли у устройства файл. Подпись проверяется при приёме — поддельное «от Васи»
отбрасывается.

**Сервисы** (`internal/services`). Устройство публикует TCP-адрес (например `127.0.0.1:22`) под именем,
с списком допущенных устройств. Другое устройство открывает локальный порт и проксирует соединения
через QUIC-поток. Встроенный SOCKS5 (`127.0.0.1:1080`, без аутентификации, поэтому любая локальная
программа может им пользоваться) отправляет соединения **только на устройства сети** — по имени
`<имя>.svoi` или оверлейному адресу, на порты, которые это устройство опубликовало как сервисы. «Выхода в
интернет» через него нет.

**Виртуальный интерфейс** (`internal/tun`, Linux). *Осторожно:* через него любой участник сети может обратиться
к любому порту, который слушает на `0.0.0.0` на этом устройстве (как сосед по локальной сети), минуя список
допусков отдельных сервисов; включайте только там, где это приемлемо (или закройте порты файрволом для `svoi0`). Создаётся `svoi0` (MTU 1150), IP-пакеты уходят в
QUIC-датаграммы к устройству-владельцу адреса назначения. На приёме проверяется, что адрес
отправителя действительно принадлежит устройству, приславшему пакет (*cryptokey routing*), иначе пакет
отбрасывается. Имена `<имя>.svoi` записываются в блок `# BEGIN svoi … # END svoi` файла `/etc/hosts`.

**Управление чужим устройством.** RPC `api.call`: администратор присылает «вызов локального API»
(метод, путь, тело), узел-получатель выполняет его **локально**, но только для разрешённых путей
(`/api/shares`, `/api/services`, `/api/settings`, `/api/local/fs`, `/api/diag/logs`, `/api/state`) и
только если вызывающий — администратор по сертификату. Почта, чат и файлы такими запросами
недоступны.

## 5. Локальный интерфейс (`internal/api`)

Интерфейс слушает `127.0.0.1` и **не открывается без входа**. Секретов в браузер не попадает:

* **Одноразовая ссылка.** Узел печатает (а `svoi url` / `svoi open` выдают новую) ссылку
  `http://127.0.0.1:PORT/?t=<код>`: код — 192 случайных бита, **срабатывает один раз и живёт 10
  минут**. Узел меняет его на случайную **сессию** (256 бит): на сервере хранится только её хеш
  (`ui.sessions`, `0600`, переживает перезапуск), в браузере — cookie `HttpOnly; SameSite=Strict`,
  код из адресной строки убирается. Сессия живёт 14 дней и продлевается, пока ею пользуются. Кто
  увидел ссылку позже (в журнале `systemd`, в `ps`, в истории терминала), находит использованный
  или просроченный код.
* **Главный токен** (`ui.token`, `0600`) — только для командной строки (`Authorization: Bearer`);
  он нигде не печатается, не попадает в URL и cookie, и браузер его не узнаёт. Только по нему
  можно выдать ссылку для входа (`POST /api/login/code`) или выйти отовсюду (`svoi signout`).
* **Рукопожатие.** Перед первым запросом `svoi` отправляет случайное число на `/api/handshake` и
  требует HMAC этого числа под токеном. Если по адресу из `ui.addr` ответил не тот узел (файл
  устарел, порт занят другой программой), токен не отправляется.

Дополнительно:

* **DNS-rebinding:** запрос с `Host`, отличным от `127.0.0.1` / `localhost` / `::1`, получает `421`.
* **CSRF:** изменяющие запросы с cookie требуют заголовок `X-Svoi: 1` и совпадающий `Origin`.
* **Чужой контент.** Файлы из общих папок — это ввод от *других устройств*, значит, недоверенный.
  HTML и прочие активные типы отдаются как `text/plain`, везде `X-Content-Type-Options: nosniff` и
  `Content-Security-Policy: default-src 'none'; sandbox`. SVG остаётся картинкой, но без права
  исполнять скрипт.
* **Заголовки интерфейса:** CSP `default-src 'self'` без внешних источников — интерфейс не грузит
  ничего из интернета (работает офлайн) и не может быть подменён по пути.
* QR-код приглашения рисуется **на сервере** как SVG.

## 6. NAT в реальном мире

Симулятор (`internal/netsim`) проверяет логику, но не ядро. Поэтому есть стенд (`lab/`), в котором
из сетевых пространств Linux, `iptables` и `conntrack` собран мини-интернет: публичная «якорная»
машина (VPS/домашний сервер с открытым портом), два роутера с NAT и по одному устройству за каждым.
В роутерах — настоящий `MASQUERADE` (конусный NAT) или `MASQUERADE --random` (симметричный),
файрвол «как у домашнего роутера» (`INPUT DROP`, ответы разрешены) либо «разрешающий».

Результаты (`make lab`, `go test -tags lab ./lab`):

| Устройство A | Устройство B | Путь | Проверено |
|---|---|---|---|
| конусный NAT | конусный NAT | **прямой** (4 МБ файла идут, не касаясь якоря) | да |
| симметричный | конусный | через ретранслятор (якорь) | да |
| симметричный | симметричный | через ретранслятор (якорь) | да |
| конусный | конусный, файрвол «разрешающий» | прямой *не гарантируется*; связь и файл — через ретранслятор | да (проверяется только связность) |
| два устройства в одной сети **без выхода наружу** | — | по локальной сети; после смены адресов всей сети (новый роутер) находят друг друга сами по маячкам; с выключенным LAN-обнаружением — не находят (контроль) | да |
| любой | любой, `--tun` | `curl http://<имя>.svoi/…` из обычной программы, без знания о svoi | да |

Что стенд нашёл и что мы сделали:

* **Перезапущенное устройство 30 секунд не могло пользоваться ретранслятором**: оно ещё не знало,
  какие участники достижимы напрямую, а *peer-state* шёл раз в 30 с. Теперь первый `ping`
  содержит флаг `wantState`, ответ приходит сразу (≈1 с).
* **Разрешающий файрвол** принимает «непрошеные» пакеты, и `conntrack` создаёт запись по пакету
  партнёра раньше, чем мы сами что-то отправили. Последующие исходящие пакеты к этому партнёру могут
  уйти с *другого* внешнего порта, чем нам известен, — прямой путь не складывается. Типичные
  домашние роутеры так не настроены (и работают как строка «домашний файрвол» выше), но
  исключения встречаются. Связь при этом **не теряется**, она идёт через ретранслятор. Известные
  улучшения (не реализованы): синхронизированное пробитие по таймеру (как DCUtR в libp2p) и
  предсказание порта для симметричных NAT.
* Диагностика NAT считала `127.0.0.1` и приватные адреса «публичными» — исправлено.

## 7. Чего здесь нет — и почему

* **Нет глобального поиска устройств.** Чтобы устройства нашли друг друга, нужен хотя бы один
  *достижимый* участник («якорь»): белый IP, проброс UDP-порта, IPv6, либо общая LAN. Это
  принципиальная граница отказа от сервера. Расширение — публикация адресов в публичной DHT
  (например, BitTorrent mainline: пакеты svoi уже выбраны так, чтобы не конфликтовать с DHT) — **не
  реализовано**.
* **Почта без хранителя.** Письмо хранится у отправителя. Хранение на третьих устройствах (custody)
  потребовало бы доверия к посреднику и политики хранения — не реализовано.
* **Нет SMTP/IMAP-шлюза** — «почта» здесь — внутренняя почта сети, не интернет-почта.
* **Нет того, что в Tailscale делают «exit node» и «subnet router»**: пустить через устройство сети весь
  интернет-трафик или открыть подсеть за ним нельзя. Есть виртуальный интерфейс между устройствами сети и
  SOCKS5, который ведёт только на устройства сети.
* **Нет DNS-сервера (MagicDNS):** имена `<имя>.svoi` попадают в `/etc/hosts`, и только при включённом
  виртуальном интерфейсе (Linux); в браузере интерфейса устройства называются по имени без DNS.
* **Нет мобильных приложений.** Android — через Termux, iOS — нет. Проверялась только
  кросс-компиляция.
* **TUN-интерфейс только на Linux.** IPv6-путь не проверялся (в тестовом ядре нет IPv6).
* **Нет аудита.** Криптографические примитивы стандартные (Ed25519, X.509, TLS 1.3/QUIC, NaCl box,
  BLAKE2s), протокол собственный и независимо не проверялся.

## 8. Как это проверяется

| Уровень | Где | Что |
|---|---|---|
| Юнит | `internal/*/…_test.go` | сертификаты, приглашения, отзывы, MAC и формат пакетов, шары и обход путей, почта и дедупликация; **регрессионные тесты каждой уязвимости из ревью** (`security_test.go`, `anonflood_test.go`, `login_test.go`, `joinlimit_test.go`, …) — написаны вместе с исправлениями; у ключевых (QUIC Retry, права на блобы, лимит вступлений, каналы в шарах, редирект входа) проверено, что без исправления они падают |
| Симуляция сети | `internal/netsim`, `internal/meshtest` | произвольные NAT (full-cone, restricted, symmetric), потери, отключение линков: пробитие, ретрансляция, переезд устройства между сетями |
| API | `internal/api/*_test.go` | вход по одноразовой ссылке и сессии, рукопожатие, CSRF, Origin, Host, безопасная выдача файлов, валидация настроек |
| Сквозной (в процессе) | `internal/demo/demo_test.go` | четыре устройства, вступление, файлы, письма, чат, передача, управление чужим устройством |
| Два процесса | `cmd/svoi/e2e_test.go` | настоящий бинарник ×2: `init`/`invite`/`join`/`status`/`send`/`ping`, вход по ссылке, `signout`, отказ отдавать токен «самозванцу» на порту |
| Браузер | `web-e2e/` | Playwright (Chromium) против **настоящего** бэкенда `svoi demo` и настоящих процессов: все экраны, мобильный размер, файлы, почта, чат, управление, сервисы, настройки, вход и выход |
| Настоящие NAT | `lab/` | реальные процессы `svoi` в сетевых пространствах Linux (iptables + conntrack): конусные и симметричные NAT, «разрешающий» файрвол, TUN, сеть без выхода наружу (см. раздел 6) |

Запуск: `make test` (всё, кроме `lab` и браузерных), `make race`, `make lab` (нужен root), `node web-e2e/run.mjs` (нужны Node 22+ и Playwright, см. `web-e2e/run.mjs`).
