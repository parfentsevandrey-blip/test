# gatebot — торговый робот для спота Gate.io

Бот на Python для спотовой торговли на Gate.io: подключаемые стратегии, отдельный
слой риск-менеджмента, бэктест на исторических свечах и режим бумажной торговли,
который включён по умолчанию.

```
┌────────────┐   свечи, цена,   ┌────────────┐  желаемые   ┌──────────┐
│  Gate.io   │  баланс, ордера  │ Стратегия  │   ордера    │   Риск   │
│  REST API  │ ───────────────► │ grid / ema │ ──────────► │ стоп-лосс│
└────────────┘                  │ rsi / своя │             │ лимиты   │
      ▲                         └────────────┘             └────┬─────┘
      │                                                         │
      │              ┌──────────────────────────┐               │
      └───────────── │ Движок: реконсиляция     │ ◄─────────────┘
        ордера       │ желаемое ↔ фактическое   │
                     └──────────────────────────┘
```

## Ключевые решения

**Стратегия не размещает ордера.** Она описывает, какие ордера *должны* стоять на
бирже, а движок сводит это с фактическим состоянием: лишнее снимает, недостающее
выставляет, совпадающее не трогает. Поэтому обрыв связи, перезапуск процесса или
ручное вмешательство не ломают логику — на следующем тике всё сходится само.

**Риск отделён от стратегии.** Стоп-лосс, тейк-профит, трейлинг, лимит позиции и
аварийная остановка живут в `risk.py` и работают одинаково под любой стратегией.
В новой стратегии их невозможно «забыть».

**Бэктест гоняет тот же движок.** Подменяются только источник данных и часы. Код
исполнения ордеров, реконсиляции и риска — тот самый, что пойдёт в бой.

**Решения принимаются по закрытым свечам.** Текущая (незакрытая) свеча
отбрасывается: её high/low/close ещё меняются, и сигнал на ней «перерисовывается».

## Установка

```bash
cd gateio-bot
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

cp config.example.yaml config.yaml     # правьте под себя
cp .env.example .env                   # ключи API (для live)
```

Нужен Python 3.10+. Зависимости — только `requests` и `PyYAML`.

## Быстрый старт

```bash
# 1. Посмотреть параметры пары
python -m gatebot info --symbol BTC_USDT

# 2. Прогнать стратегию на истории за 90 дней
python -m gatebot backtest --days 90

# 3. Запустить на виртуальных деньгах (реальные котировки, ордера не уходят на биржу)
python -m gatebot run

# 4. Один тик и выход — удобно для проверки конфига
python -m gatebot run --once
```

## Команды

| Команда | Что делает |
|---|---|
| `run` | Торговый цикл. По умолчанию paper, `--live` — реальные деньги |
| `run --once` | Один тик и выход |
| `backtest --days N` | Бэктест на истории с биржи |
| `backtest --csv f.csv` | Бэктест на своих данных (`ts,open,high,low,close,volume`) |
| `backtest --save-csv out.csv` | Сохранить кривую капитала |
| `arb` | Треугольный арбитраж: наблюдение и статистика |
| `arb --triangles` | Показать все найденные циклы |
| `arb --execute` | Арбитраж с реальными сделками |
| `balance` | Балансы спот-аккаунта (нужны ключи) |
| `info [ПАРА]` | Точности, минимальные объёмы, текущая цена |
| `strategies` | Список доступных стратегий |
| `reset` | Снять аварийную остановку, удалив файл состояния |

Общие флаги (`--symbol`, `--interval`, `--strategy`, `-c`, `-v`) работают и до
подкоманды, и после неё.

## Стратегии

### `grid` — сетка

Разбивает коридор `[lower, upper]` на уровни; ниже цены держит покупки, выше —
продажи. Каждое колебание внутри коридора даёт покупку внизу и продажу вверху.
Зарабатывает на боковике, теряет на сильном тренде.

```yaml
strategy:
  name: grid
  params:
    levels: 12
    order_quote: 20          # сумма на один уровень, USDT
    lower: 55000             # если не задать границы — возьмётся
    upper: 72000             # ±range_pct вокруг цены запуска
    geometric: true          # равные шаги в процентах, а не в долларах
    max_orders_per_side: 5
    exit_on_break: false     # закрыть позицию при выходе цены из коридора
```

Сетка строится один раз и не «едет» за ценой — иначе ордера переставлялись бы
каждый тик, платя комиссию впустую. Продажи выставляются только в пределах реально
имеющейся базовой валюты: на споте шорта нет.

### `ema_cross` — пересечение EMA

Вход в лонг при пересечении быстрой EMA снизу вверх, выход — при обратном.
Фильтр `trend` отсекает сделки против основного движения.

```yaml
strategy:
  name: ema_cross
  params:
    fast: 12
    slow: 26
    trend: 100          # 0 — выключить фильтр
    order_quote: 100    # или equity_pct: 0.25 — доля счёта на сделку
```

### `rsi_reversion` — возврат к среднему

Покупает, когда RSI **выходит** из зоны перепроданности, закрывает в зоне
перекупленности. Именно выход, а не «RSI < 30»: в затяжном падении RSI держится
ниже 30 неделями, и вход по факту низкого RSI ловит нож.

```yaml
strategy:
  name: rsi_reversion
  params:
    period: 14
    oversold: 30
    overbought: 70
    order_quote: 100
```

## Риск-менеджмент

```yaml
risk:
  stop_loss_pct: 0.03        # выход при -3% от средней цены входа
  take_profit_pct: 0.06      # выход при +6%
  trailing_stop_pct: 0.02    # выход при откате на 2% от максимума позиции
  max_position_quote: 300    # максимум денег в позиции (или max_position_pct)
  max_daily_loss_pct: 0.05   # стоп на день при -5% от капитала на начало дня
  max_drawdown_pct: 0.15     # полная остановка при просадке 15% от пика
  max_open_orders: 20
```

Порядок проверок: аварийная остановка → защита позиции → ограничение размера.
`max_daily_loss_pct` и `max_drawdown_pct` — **липкие**: после срабатывания бот
закрывает позицию и больше не входит, даже если счёт восстановился. Снять блокировку
можно только вручную командой `reset`. Так и задумано: если сработал дневной лимит,
решение о продолжении принимает человек.

Стоп-лосс и тейк-профит исполняются самим ботом по рынку, а не условными ордерами
на бирже. Значит, они работают, **только пока процесс запущен**. Если бот упадёт,
позиция останется без защиты — для боевого запуска ставьте его под `systemd`
с автоперезапуском.

## Треугольный арбитраж

Отдельный режим (`arb`), не связанный со стратегиями и свечами. Внутри одной
спотовой биржи возможен только треугольный арбитраж: цепочка из трёх сделок
возвращает в исходную валюту, и если произведение курсов после комиссий больше
единицы, разница остаётся нам.

```
USDT ──купить BTC──► BTC ──купить ETH за BTC──► ETH ──продать за USDT──► USDT
```

Ни плеча, ни переводов между биржами, ни ставки на движение цены: позиция живёт
секунды и закрывается в той же валюте, с которой начали.

```bash
python -m gatebot arb --triangles          # какие циклы вообще существуют
python -m gatebot arb --once               # один скан, подробный отчёт
python -m gatebot arb --duration 3600      # час наблюдения со статистикой
python -m gatebot arb --execute            # реальные сделки (ключи + подтверждение)
```

### Как считает

Скан идёт в два этапа. Сначала один запрос `/spot/tickers` отдаёт верх стакана по
всем ~2200 парам, по ним грубо оцениваются все циклы и отбираются кандидаты.
Затем для кандидатов запрашиваются живые стаканы и цикл считается честно.

Два этапа нужны потому, что тикеры кешируются: на BTC_USDT `lowest_ask` из тикера
регулярно оказывается **ниже** реального лучшего ask в стакане. Торговать по таким
данным — гарантированный убыток; сузить 252 цикла до восьми кандидатов — годятся.

Точный расчёт учитывает то, на чём такие боты обычно и горят:

- **Проход по стакану.** На лучшей цене стоит ограниченный объём; заявка крупнее
  исполняется по нескольким уровням, и средняя цена хуже. Прибыль считается по
  реальному VWAP, а не по верхней строке.
- **Комиссия трижды.** Три сделки — три комиссии, каждая с получаемой валюты.
- **Минимальные объёмы.** Цикл, где второе звено не проходит по `min_quote_amount`,
  отбрасывается целиком: иначе первая сделка исполнится, а вторая нет.
- **Глубина.** Если объём упирается в конец видимого стакана, размер уменьшается
  бинарным поиском до исполнимого; если не находится — цикл пропускается.

### Риск оборванного звена

Главная опасность арбитража — не ошибка в расчёте, а зависшее звено: первая сделка
прошла, вторая нет, и вместо замкнутого цикла остаётся открытая позиция в случайной
монете. Поэтому исполнитель:

- считает каждое следующее звено от **фактически полученного** объёма;
- перед звеном ограничивает объём реальным балансом (комиссию могли списать
  из получаемой валюты);
- при обрыве откатывается — продаёт купленное обратно в базовую валюту;
- встаёт после `max_failures` оборванных циклов подряд.

Один случай не лечится: если не исполнилось **третье** звено, откат — это ровно та
же сделка, что и само звено. Тогда бот честно сообщает, в какой монете и сколько
зависло, и требует ручного вмешательства, а не рапортует об успехе.

### Что показало наблюдение

Замер на живом рынке Gate.io, 43 скана по 252 цикла, размер 100 USDT. Комиссия
обнулена намеренно — чтобы увидеть само расхождение цен:

```
расхождение по тикерам (лучший цикл):  медиана +0.0023%  максимум +0.0155%
проверка по живому стакану (топ-3):    медиана -0.0091%  максимум +0.0181%

порог безубыточности при 0.2%:  +0.600%
порог безубыточности при 0.1%:  +0.300%
```

Ни одного случая выше порога. Максимальное расхождение за всё наблюдение —
0.018% при необходимых 0.6%: разрыв в 33 раза. Рынок согласован до сотых долей
процента, и вся разница уходит в комиссию задолго до того, как её станет видно.

Это ожидаемо. Треугольный арбитраж на крупной бирже выбирают алгоритмы с
серверами в том же дата-центре, доступом к WebSocket-потоку стакана и комиссией
уровня VIP. Цикл живёт миллисекунды; REST-опрос раз в две секунды физически не
успевает. Чтобы у такой схемы появился шанс, нужны все три вещи сразу: комиссия
0.1% и ниже (GT/VIP), WebSocket вместо REST и колокация. Даже тогда борьба идёт
за доли базисного пункта.

Поэтому режим по умолчанию — наблюдение. Счётчики (сколько циклов проверено,
максимальное расхождение, сколько прошло порог) отвечают на вопрос «есть ли тут
что ловить» до того, как в дело пойдут деньги. Запустите `arb --duration 3600` на
своей комиссии и своём канале и посмотрите на цифры сами.

## Своя стратегия

```python
from gatebot.strategies.base import Strategy, StrategyContext
from gatebot.types import Decision, DesiredOrder, Side

class MyStrategy(Strategy):
    """Одна строка описания — попадёт в вывод `strategies`."""

    key = "my_strategy"
    warmup = 50          # сколько свечей нужно перед первым решением

    def decide(self, ctx: StrategyContext) -> Decision:
        # ctx.candles — закрытые свечи по возрастанию времени
        # ctx.price, ctx.position, ctx.equity, ctx.quote_free, ctx.base_free
        if ctx.position.is_open:
            return Decision(flatten=True, note="закрываемся")
        return Decision(
            desired=[DesiredOrder("entry", Side.BUY, amount=..., price=...)],
            note="почему входим",
        )
```

Зарегистрируйте класс в `gatebot/strategies/__init__.py` → `REGISTRY`.

Два правила:

1. `desired` — **полный** желаемый набор ордеров, а не дельта. Чего в нём нет, то
   будет снято.
2. `client_id` должен быть стабильным: один и тот же логический ордер обязан
   получать один и тот же id от тика к тику, иначе движок снимет и переставит его.

Рыночный ордер (`price=None`) срабатывает по фронту: пока стратегия просит тот же
`client_id`, повторно он не отправляется — иначе сигнальная стратегия докупала бы
на каждом тике.

## Реальная торговля

```bash
# .env
GATEIO_API_KEY=...
GATEIO_API_SECRET=...
```

Ключ создаётся в Gate.io: **Профиль → API Keys → Create API Key**.

- Права: только **Spot Trade**. Вывод средств (Withdraw) не включать никогда.
- Ограничьте ключ по IP-адресу сервера.
- Ключи читаются только из переменных окружения; в конфиг они не пишутся, `.env` в `.gitignore`.

```bash
python -m gatebot run --live
```

Запуск потребует ввести подтверждение с клавиатуры. Пропустить его можно флагом
`--yes` — он нужен для `systemd`, но до этого стоит дойти осознанно.

Пример юнита:

```ini
[Unit]
Description=gatebot
After=network-online.target

[Service]
WorkingDirectory=/opt/gatebot
EnvironmentFile=/opt/gatebot/.env
ExecStart=/opt/gatebot/.venv/bin/python -m gatebot run --live --yes
Restart=always
RestartSec=10

[Install]
WantedBy=multi-user.target
```

## Что важно знать до запуска на деньгах

- **Бэктест — не обещание.** Он не моделирует стакан, частичное исполнение лимиток
  и проскальзывание крупных заявок. Прибыль на истории не переносится на будущее.
- **Комиссии решают.** При 0.2% за сделку сетка со 140 сделками отдаёт бирже
  около 3% депозита за месяц. Считайте комиссию частью стратегии, а не сноской.
- **Учёт позиции ведётся по сделкам самого бота.** Монеты, купленные руками на том
  же аккаунте, он своими не считает и не продаёт. Для чистого учёта лучше завести
  отдельный суб-аккаунт: капитал в отчётах и риск-лимитах считается по всей паре.
- **Начинайте с `paper`.** Дайте ему поработать несколько дней на реальных
  котировках, сверьте логи с графиком, и только потом переходите на `live`.
- **Первый живой запуск — минимальной суммой** и с заданными `stop_loss_pct` и
  `max_daily_loss_pct`.

## Структура

```
gatebot/
  types.py           Свеча, ордер, позиция, желаемый ордер
  indicators.py      SMA, EMA, RSI, ATR, пересечения — чистый Python
  config.py          Загрузка и валидация YAML + .env
  exchange/
    base.py          Интерфейс биржи
    gateio.py        REST-клиент Gate.io v4 (HMAC-SHA512)
    paper.py         Симулятор: реальные котировки, виртуальные деньги
  strategies/
    base.py          Контракт стратегии
    grid.py          Сетка
    ema_cross.py     Пересечение EMA
    rsi_reversion.py Возврат к среднему по RSI
  risk.py            Стопы, лимиты, аварийная остановка
  arbitrage/
    triangle.py      Поиск циклов и расчёт по стакану
    scanner.py       Отбор по тикерам + проверка по живому стакану
    executor.py      Исполнение трёх звеньев с откатом
    runner.py        Цикл сканирования и статистика
  engine.py          Тик, реконсиляция ордеров, учёт исполнений
  backtest.py        Прогон по истории + метрики
  state.py           Состояние между перезапусками
  cli.py             Командный интерфейс
```

## Отказ от ответственности

Код предоставлен как есть, для образовательных целей. Торговля криптовалютой
сопряжена с риском полной потери средств. Ответственность за использование бота
и за все совершённые им сделки несёт пользователь.
