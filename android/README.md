# Veil — VPN на свободных протоколах

Android-приложение, которое поднимает системный VPN и уводит весь трафик
устройства в сеть Tor, автоматически подбирая способ обхода блокировки.
Ничего вводить не нужно: ни адрес сервера, ни ключ, ни логин. Всё, что
использует приложение, — свободное ПО и публичная инфраструктура.

Интерфейс написан по Material 3 Expressive (Compose Material3 1.5.x): морфинг
формы у главной кнопки, пружинная моторика `MotionScheme.expressive()`,
`ShortNavigationBar`, `MediumFlexibleTopAppBar`, `ButtonGroup`,
`LoadingIndicator`, динамическая палитра Material You. `compileSdk`/`targetSdk`
— 37.

## 1. Что тут вообще происходит

```
   приложения на телефоне
            │  IP-пакеты
            ▼
   ┌────────────────────┐
   │  VpnService (TUN)  │  10.55.0.1/24, маршрут 0.0.0.0/0 и ::/0
   └─────────┬──────────┘
             │ file descriptor
             ▼
   ┌────────────────────────────────────────────┐
   │  veiltun (Go + gVisor netstack)            │
   │  · терминирует TCP, отдаёт в SOCKS5        │
   │  · DNS перехватывает и уводит внутрь       │
   │  · UDP отбрасывает (Tor его не умеет)      │
   └─────────┬──────────────────────────────────┘
             │ SOCKS5 127.0.0.1:9050
             ▼
   ┌────────────────────┐      ┌──────────────────────────────┐
   │  tor (libtor.so)   │◄────►│ lyrebird / snowflake         │
   │  control port      │  PT  │ obfs4 · meek · webtunnel     │
   └─────────┬──────────┘      └──────────────────────────────┘
             │                   (в том же libgojni.so, что и veiltun)
             ▼
        сеть Tor
```

Ключевая деталь: собственный пакет приложения исключён из VPN
(`addDisallowedApplication`). Иначе сокеты самого tor и транспортов ушли бы
обратно в тот же туннель, который они должны питать, и не поднялось бы ничего.

## 2. Что работает «из коробки», без ввода серверов

Вопрос «какие ещё стандарты можно внедрить, чтобы работало без вбивания
данных» на практике сводится к одному критерию: **у протокола должна быть
публичная инфраструктура, адреса которой уже зашиты в клиент**. Таких
вариантов немного.

### Реализовано

| Маршрут | Что прячет | Откуда берёт адреса | Цена |
|---|---|---|---|
| **Tor напрямую** | ничего | директории-авторити зашиты в `tor` | быстрый |
| **obfs4** (lyrebird) | сигнатуру протокола | встроенные мосты + Moat API | быстрый |
| **WebTunnel** | всё внутри обычного HTTPS к живому сайту | мосты из Moat / вручную | средний |
| **meek_lite** | domain fronting через CDN | URL и front зашиты | медленный |
| **Snowflake** | нет постоянного адреса вообще | брокер + domain fronting / AMP-кэш | медленный |

Все пять не требуют от пользователя ни одного поля ввода. Списки встроенных
мостов лежат в `app/src/main/assets/builtin_bridges.json` (снимок с
`bridges.torproject.org/moat/circumvention/builtin`) и обновляются на лету
при каждом подключении.

### Почему не WireGuard, Shadowsocks, VLESS, Hysteria и подобное

Это транспорты «точка-точка»: они прекрасны, но требуют сервера, которого у
пользователя нет. Без адреса и ключа их нельзя запустить в принципе. Из них
нельзя сделать «нажал кнопку и работает», можно только «нажал кнопку и
подключился к чужому серверу», а это уже совсем другой продукт с другой
моделью доверия. Архитектура приложения (`TransportEngine` → локальный
SOCKS5) оставляет для них место, но по умолчанию они не включены.

### Что рассматривалось и не вошло

* **Psiphon** — единственный реальный кандидат «второй сети из коробки»:
  открытый код (GPLv3), встроенный список серверов, работает без настройки.
  Не включён: требует собственных `PropagationChannelId`/`SponsorId` от
  Psiphon Inc. и завязан на централизованно управляемую сеть. Архитектурно
  добавляется одним классом-движком.
* **Conjure** (refraction networking) — сильнее Snowflake по устойчивости, но
  клиент не входит в IPtProxy, потребовалась бы отдельная сборка Go-модуля.
* **I2P** — не заменяет VPN: наружу ходит только через редкие outproxy.
* **Lantern** — не полностью открыт.

## 3. Как приложение борется с блокировкой

Это основная содержательная часть, а не просто «включили Tor».

### 3.1. Сначала измеряем сеть, потом выбираем

`net/Probe.kt` параллельно проверяет пять вещей и делает это **настоящими
сетевыми пробами**, а не догадками:

1. **TCP до директорий Tor** — маршрутизируется ли протокол вообще.
2. **TCP до опубликованных obfs4-мостов** — не выжжены ли адреса по IP.
3. **TCP до крупных CDN** (`www.phpmyadmin.net`, `app.datapacket.com`) —
   жив ли путь, который нужен meek и Snowflake.
4. **Полный TLS-хендшейк к `www.torproject.org`** — если TCP открывается, а
   рукопожатие рвётся, это классическая подпись фильтрации по SNI.
5. **STUN binding request по UDP** — жив ли UDP; без него у Snowflake нет
   канала данных.

Из этих пяти ответов строится ранжирование маршрутов (`NetworkProbe.rank`).

### 3.2. Лестница эскалации

`tor/StrategyPlanner.kt` собирает порядок попыток из четырёх источников, по
убыванию силы:

1. **Что уже работало в этой конкретной сети.** `data/StrategyMemory.kt`
   помнит результат по непрозрачному отпечатку сети. Отпечаток строится из
   типа транспорта, DNS-серверов линка и MCC SIM-карты и сразу хешируется —
   разрешение на геолокацию (которое понадобилось бы для SSID) не
   запрашивается вообще.
2. **Что Tor Project рекомендует для этой страны.** Те же данные, что
   использует Tor Browser Connect Assist:
   `moat/circumvention/settings`. Оффлайн-снимок лежит в
   `assets/circumvention_map.json`.
3. **Результаты проб** из пункта 3.1.
4. **Статическая лестница** — от дешёвого к дорогому, чтобы неверная догадка
   выше по списку никогда не выкидывала рабочий маршрут.

Последней ступенью всегда идёт Snowflake, а после него — Snowflake с
рандеву через **AMP-кэш Google** вместо domain fronting: это выживает там, где
заблокирован уже сам фронтированный запрос к брокеру.

### 3.3. Бюджет времени и детектор «залипания»

Каждой ступени даётся свой бюджет (`StrategyPlanner.budgetMillis`): obfs4 —
60 с, meek — 90 с, Snowflake — 120 с. Это не произвол: obfs4 либо
подключается быстро, либо не подключается вовсе, а Snowflake сначала должен
найти волонтёрский прокси и штатно тратит полминуты до первого байта.
Обрубить Snowflake по бюджету obfs4 — классический способ ошибочно решить, что
не работает ничего.

Плюс отдельно отслеживается **отсутствие прогресса**: если процент bootstrap
не двигается 35 секунд, ступень признаётся мёртвой досрочно. Именно это
отличает инструмент, который честно перебирает варианты, от того, что пять
минут показывает «10 %».

### 3.4. Когда и мосты не работают

Встроенные мосты публичны, поэтому цензор перечисляет и блокирует их первыми.
Ответ на это — три уровня:

* **Обновление списка** с `moat/circumvention/builtin` при каждом коннекте.
* **Запрос приватных мостов через CAPTCHA прямо в приложении**
  (`moat/fetch` + `moat/check`). Это важно именно тогда, когда сайт
  `bridges.torproject.org` недоступен: решать капчу в приложении можно, а
  открыть сайт — нет.
* **Фронтированный запрос к самому API.** Если прямой HTTPS к Moat не проходит,
  запрос повторяется **через meek**: приложение поднимает lyrebird, само
  открывает SOCKS5-соединение и кладёт аргументы транспорта в поля
  username/password ровно так, как это делает tor (`net/Socks5.kt`,
  `SocksProxy.withTransportArgs`). Дальше поверх этого сокета вручную
  говорится HTTPS (`net/SimpleHttp.kt`), потому что штатный HTTP-клиент
  Android не даёт задать SOCKS-креденшелы.

И, наконец, Snowflake: у него **нет постоянного адреса, который можно
заблокировать**. Именно поэтому он последний в лестнице, а не первый — он
работает почти всегда, но медленно.

### 3.5. Отдать канал другим

В настройках есть переключатель «работать прокси Snowflake»: устройство
становится одним из тех волонтёрских узлов, через которые кто-то за файрволом
дотягивается до Tor. Это единственное, чем пользователь без цензуры может
напрямую помочь пользователю с цензурой.

## 4. Реалии блокировок 2026 и что мы делаем против них

Всё ниже — реакция на публичные разборы того, как в России работают ТСПУ.
Важная оговорка: пороги и константы там — реконструкция чёрного ящика по
наблюдениям, а не опубликованные значения, и ТСПУ децентрализована — у МТС,
Ростелекома и Билайна параметры различаются. Поэтому мы закладываемся на
запас, а не подгоняемся под конкретные цифры.

### 4.1. Что изменилось: детект стал составным

До 2024 блокировка была сигнатурной: фиксированные байты, списки SNI, блоклисты
IP. К 2026 это заменилось схемой «И» из трёх признаков — блокировка срабатывает,
когда выполняются **все три одновременно**:

| Признак | Что смотрят | Что это значит для нас |
|---|---|---|
| **1. Куда** | AS и подсеть назначения: зарубежные ДЦ, часть российских облаков | Наши фронтированные транспорты идут в крупные CDN, которые целиком не блокируют из-за легального контента. Признак не срабатывает. |
| **2. Чем** | JA3/JA4-отпечаток Client Hello. Подозрительны статичные библиотечные отпечатки и устаревшие версии браузеров | Прямо управляем: см. 4.2 |
| **3. Как** | Больше трёх параллельных TLS-хендшейков к одному имени в окне ~350–400 мс | Прямо управляем: см. 4.3 |

Важно, что **obfs4 попадает под первый признак**: он терминируется на мосту в
хостинге, а это ровно тот тип назначения, который ищут. Плюс работа USENIX
Security 2024 по TLS-in-TLS показывает >70 % TPR по размерам и таймингам
бёрстов в том числе для obfs4 и REALITY. Мы это учли в ранжировании: при
признаках заморозки obfs4 и прямой Tor опускаются в самый низ лестницы.

### 4.2. Отпечаток Client Hello — настройка, а не наследство

Встроенные строки мостов приходят с тем отпечатком, который был актуален на
момент их публикации; часть до сих пор просит `utls=hellorandomizedalpn`.
Рандомизация обходит блоклист точных хешей, но сама по себе аномальна: ни один
настоящий клиент не меняет Client Hello на каждом соединении.

Поэтому профиль стал локальным решением (`model/TlsProfile.kt`,
настройка в разделе «Отпечаток»):

* по умолчанию **Firefox** — «лояльный» профиль, и, в отличие от Chrome, не тот,
  на который по умолчанию садится прокси-софт;
* доступны Chrome, Edge, Android-стек и рандомизация;
* всегда используются варианты `_Auto`, то есть самый свежий Client Hello,
  который знает встроенный uTLS, — пиннинг старой версии сам по себе улика.

Два транспорта принимают **разные наборы имён**: у lyrebird полная таблица uTLS,
у Snowflake — короткая, без Edge и без Android. Неизвестное имя заставляет
транспорт не стартовать, поэтому каждый профиль объявляет свой запасной вариант.

Отдельно у Snowflake есть собственное рукопожатие **DTLS**, которого настройка
выше не касается. Для него прокидывается `covertdtls-config`, по умолчанию
`mimic` — имитация Client Hello настоящего браузера.

### 4.3. Темп рукопожатий

`net/HandshakeGovernor.kt` пропускает не больше **двух** одновременных
рукопожатий к одному хосту и держит между их началами не меньше **450 мс** —
с запасом относительно наблюдаемого порога. Через него проходят и активные
пробы, и запросы к API мостов.

Дополнительно планировщик выдаёт tor **меньше мостов**: три для obfs4 и
WebTunnel, ровно один для meek и Snowflake (там строка моста — это конфигурация,
а не адрес). Больше мостов — не лучше: tor открывает соединение к каждому, а
веер почти одновременных хендшейков и есть тот самый третий признак.

Самому Tor этот веер несвойственен: клиент на мостах держит одно-два соединения
к одному узлу и мультиплексирует по ним все цепочки. Мультиплексирование — первый
из архитектурных принципов устойчивости, и он у нас есть бесплатно.

### 4.4. «Заморозка» — и почему нельзя просто повторить

Современная блокировка **не сбрасывает** соединение. TCP-хендшейк проходит,
Client Hello уходит, и дальше пакеты просто перестают форвардиться: окно
заполняется, приложение стоит, через ~120 секунд наступает таймаут. Для
приложения это неотличимо от медленной сети — и именно поэтому это надо уметь
отличать.

`net/Probe.kt` теперь замеряет время TCP-соединения и время рукопожатия
раздельно (та же методика, что `time_connect` против `time_appconnect` у curl) и
выдаёт один из четырёх вердиктов: **открыто**, **TCP заблокирован**,
**рукопожатие сброшено**, **заморожено**. Проверяются два имени: цензурируемое
и нейтральное — контроль, который отделяет фильтрацию по имени от общей.

Из вердикта следует поведение. Повтор внутри окна штрафа бесполезен, а смена
отпечатка под нагрузкой, по наблюдениям, продлевает штраф до ~600 секунд **на
все** TLS-соединения к этому узлу. То есть очевидный рефлекс — «сразу попробовать
другой транспорт на тот же мост» — оказывается худшим из возможных ходов.
Поэтому `data/EndpointCooldown.kt` откладывает замороженный адрес на 150 секунд,
а при повторной заморозке — на 650, и планировщик его в это время не предлагает.
Отложенные адреса видны в «Диагностике».

### 4.5. Локальный прокси — дыра, о которой обычно молчат

Мобильные клиенты на xray/sing-box поднимают локальный SOCKS5 **без
аутентификации**. Любое приложение на устройстве может к нему подключиться в
обход VpnService; в методичках по выявлению средств обхода прямо перечислены
порты 1080, 9000, 5555, 16000–16100, 3128, 8080 и так далее. Изоляция в private
space не помогает: loopback остаётся общим.

Что сделано:

* **Порт случайный.** `SocksPort auto` вместо 9050 — на «известном» порту мы не
  отвечаем.
* **HTTP-прокси выключен.** `HTTPTunnelPort 0`: 8118 — классический порт Privoxy
  и лишняя зацепка, а нам он не нужен.
* **Видимость вместо умолчания.** Экран «Диагностика» показывает список портов,
  которые приложение держит открытыми, и что через них может сделать соседнее
  приложение. Это то, чего в других клиентах нет вовсе.

Что **не** сделано и почему. Правильный ответ — unix-сокет в приватном каталоге
приложения: до него не дотянется никто. Нативный туннель это уже умеет
(`Config.SocksNetwork = "unix"`), и torrc это поддерживает. Мешает встроенный
`TorService`: он безусловно парсит `net/listeners/socks` как число и падает с
`NumberFormatException` на значении `unix:/path`, а необработанное исключение в
потоке убивает процесс. Как только это поправят выше по течению (или мы начнём
запускать tor сами) — это изменение в одну строку.

Стоит трезво оценить и масштаб риска именно для нас. У VLESS-клиента чужое
подключение к локальному прокси выдаёт адрес сервера и помогает деанонимизации.
У нас за прокси стоит Tor: соседнее приложение получит выходной узел Tor, а не
адрес пользователя. Остаётся отпечаток «на устройстве стоит средство обхода» —
и его случайный порт снижает, но не убирает.

### 4.6. Поведенческий анализ: чего нельзя подделать статикой

Разбор детекта MTProto показывает, что после рукопожатия смотрят на форму
потока: гистограммы размеров пакетов, симметрию направлений и — отдельно —
**регулярные keep-alive пинги** как маркер долгоживущего соединения,
нехарактерного для веба.

Из этого следуют две конкретные правки, обе уже внесены.

**Убран фиксированный keepalive.** В torrc стояло `KeepalivePeriod 60`. Это ровно
тот метроном, который ищут: мелкие пакеты через равный интервал. Теперь значение
оставлено по умолчанию, а соединение поддерживает рандомизированный
`ConnectionPadding` — он же и маскирует моменты начала и конца сессии.

**Отпечаток стал разным у разных установок.** В том же разборе аномалией названо
«к одному IP подключаются десятки и сотни клиентов с идентичным TLS-отпечатком
одной и той же, часто устаревшей, версии браузера». Приложение, зашивающее один
Client Hello, производит ровно такую картину в масштабе. Поэтому профиль по
умолчанию — **«Автоматически»**: он выбирается один раз при установке из набора
правдоподобных (Firefox, Chrome, Edge, Android-стек) и дальше не меняется.
Стабильность здесь так же важна, как разброс: смена отпечатка посреди сессии, по
наблюдениям, продлевает штраф, а не снимает его. Рандомизация в этот набор не
входит намеренно — она сама по себе признак.

### 4.7. Почему память по сетям — это не оптимизация, а необходимость

В опросе по одной из статей 54,55 % респондентов ответили, что обход «работает
по-разному в разных сетях», и лишь 8,33 % — что стабильно. Это не шум: ТСПУ —
единая политика при распределённом исполнении, у операторов различаются
топология, полнота охвата трафика и загрузка оборудования, а асимметричная
маршрутизация местами вообще лишает анализатор половины сессии.

Значит, «какой транспорт работает» — свойство не страны и не приложения, а
**конкретной сети в конкретный момент**. Поэтому `data/StrategyMemory.kt`
запоминает результат по непрозрачному отпечатку сети и поднимает наверх то, что
здесь уже сработало, а `EndpointCooldown` не даёт долбиться в адрес, который
сейчас под штрафом. Универсального ответа тут нет — есть только быстрый способ
заново найти локальный.

### 4.8. Локальные сайты мимо тоннеля

Самая частая практическая жалоба на любой VPN в России — перестают открываться
российские сайты и банковские приложения: блокировка идёт по IP, и соединение
рвётся на TCP-хендшейке, а многие сервисы вдобавок сами не принимают трафик с
выходных узлов Tor.

Приложение умеет это обходить двумя способами:

* **По приложениям** (экран «Приложения») — банк целиком выводится из VPN. Самый
  безопасный вариант: решение принимается один раз и не зависит от разбора
  трафика.
* **По именам** (переключатель в «Настройках», по умолчанию **выключен**) — имена
  на `.ru`, `.рф`, `.su`, `.by`, `.kz` резолвятся через DNS локальной сети и
  открываются напрямую. Это чинит браузер, который нельзя «вывести целиком».

Как это устроено, и почему решение принимается по имени, а не по адресу: с
`AutomapHostsOnResolve` tor подменяет любой разрешённый адрес виртуальным, так
что на момент соединения настоящего IP просто нет. Поэтому совпавшее имя
резолвится в обход тоннеля, а полученные адреса запоминаются на время их TTL —
и только они дальше набираются напрямую. Адрес, который никто не резолвил, идёт
в тоннель как обычно: приложение с зашитым IP не может случайно выпрыгнуть
наружу.

Цена честная и названа прямо в интерфейсе: эта сеть увидит, какими локальными
сервисами вы пользуетесь. Именно поэтому по умолчанию выключено.

### 4.9. Почему всё ещё нет VLESS + Reality / XHTTP

Это то, что сегодня даёт скорость, и это же то, что требует сервера. У Reality
своя уязвимость — он маскирует рукопожатие, но не последующий профиль трафика, и
под нагрузкой выдаёт себя поведением; ответ на это (XHTTP: разделение потоков на
отдельные HTTP-транзакции плюс `xPaddingBytes`) — тоже про сервер, который надо
где-то взять и оплатить.

Архитектура приложения (`TransportEngine` → локальный SOCKS5) оставляет для
такого движка место, и добавление свелось бы к встраиванию xray-core и импорту
конфигурации. Но это уже другой продукт с другой моделью доверия: «нажал кнопку
и работает» превращается в «нажал кнопку и подключился к чьему-то серверу».
Пока приложение остаётся тем, чем заявлено, — работающим из коробки на публичной
инфраструктуре.

Заодно из тех же разборов: WireGuard, gRPC и MTProto-прокси попали под волны
блокировок, SSH — нет. Это лишний довод, что добавление ещё одного
«точка-точка» транспорта не решило бы задачу.

### 4.10. Форма трафика

Против поведенческого анализа в torrc теперь явно включено то, что обычно
выключают ради батареи:

```
ConnectionPadding 1        # прячет моменты начала и конца соединения
ReducedConnectionPadding 0
CircuitPadding 1           # прячет форму того, что внутри
ReducedCircuitPadding 0
```

И главный структурный аргумент: у Snowflake канал данных — **WebRTC поверх
UDP**. Все перечисленные TCP-эвристики к нему просто неприменимы, это другой
класс детектора. Поэтому при обнаружении заморозки Snowflake получает наивысший
приоритет, а не остаётся последней ступенью «на всякий случай».

### 4.11. Отмена подключения

Отдельно исправлено то, что ломало работу с приложением: отмена подключения
могла зависнуть навсегда, и выйти из этого состояния получалось только снятием
процесса из меню Android.

Причина структурная. Отмена — это не установка флага: tor живёт в связанном
сервисе, транспорты — это Go по ту сторону JNI, и ни то, ни другое нельзя
прервать посреди вызова. `cancel()` замечается только на следующей точке
приостановки, до которой может быть несколько секунд, а если что-то заклинило —
вечность. Плюс `onDestroy()` отменял ту самую область корутин, в которой шла
уборка, так что она не доводилась до конца и сервис навсегда оставался на
переднем плане.

Что сделано:

* уборка вынесена в область, живущую дольше сервиса, и больше не отменяется его
  уничтожением;
* ей выдан жёсткий бюджет: работа идёт в отдельной задаче, ожидание — через
  `join()` под таймаутом, поэтому даже заблокированный нативный вызов не держит
  приложение. Он доработает на своём потоке, а сервис уйдёт;
* повторное нажатие «Отмена» больше не игнорируется — оно трактуется как «первая
  попытка застряла» и гасит всё немедленно;
* `stopSelfResult` вместо `stopSelf`, поэтому повторное подключение во время
  уборки не убивает уже перезапущенный сервис;
* `TorController.start()` больше не падает на оставшемся с прошлого раза
  биндинге, а прибирает его и продолжает;
* цикл перебора маршрутов слушает отмену собственной задачи, а не области
  сервиса;
* на стороне UI добавлена страховка: если «Отключаюсь» держится дольше 12 секунд,
  экран возвращается в исходное состояние, чтобы можно было просто нажать
  «Подключить» ещё раз.


### 4.12. Почему не работал вообще ни один способ

Это оказалась не блокировка. Три ошибки в самом приложении, каждая из которых
выглядела снаружи ровно как цензура.

**Tor перезапускался на каждую ступень лестницы.** Под каждый маршрут писался
свой torrc, tor останавливался и поднимался заново. Это не только полминуты до
первого байта: `TorService` сериализует старт на статическом замке, сам tor
держит замок на своём каталоге данных, и предыдущий экземпляр часто ещё не
завершился, когда стартует следующий. Начиная со второй ступени «ничего не
работает» — это были мы, а не сеть.

Теперь tor стартует **один раз**, со всеми `ClientTransportPlugin` сразу, а
маршрут переключается по управляющему порту: `RESETCONF Bridge UseBridges`,
затем `SETCONF` с новыми мостами. Секунда вместо минуты — и, что важнее,
надёжно вместо «как повезёт».

**При `DisableNetwork 1` у tor нет ни SOCKS-, ни DNS-слушателя.** Приложение
поднимало tor с выключенной сетью (чтобы первый маршрут выбирался осознанно, а
не «как получится»), после чего спрашивало у него `GETINFO net/listeners/socks`
— и получало пустую строку, что читалось как «tor не запустился».

Это не догадка, это проверено на настоящем tor 0.4.8:

```
GETCONF DisableNetwork      -> 250 DisableNetwork=1
GETINFO net/listeners/socks -> 250-net/listeners/socks=
GETINFO net/listeners/dns   -> 250-net/listeners/dns=
```

В исходниках это записано прямым текстом: `retry_all_listeners` получает
`DisableNetwork` вторым аргументом, и её собственный комментарий гласит —
«если `close_all_noncontrol` истинно, мы открываем только управляющие
слушатели, а все остальные закрываем».

**`SocksPort auto` меняет порт при каждом включении сети.** «auto» — это порт
ноль, то есть эфемерный, и tor берёт новый при каждом открытии слушателя. Та же
проверка:

```
DisableNetwork=0 -> socks = 127.0.0.1:43335
DisableNetwork=1 -> socks = (пусто)
DisableNetwork=0 -> socks = 127.0.0.1:39025
```

Любой адрес, прочитанный один раз при старте, со второй ступени неверен.

Первую ступень при этом tor получает **сразу в torrc** — с мостами и с
включённой сетью, ровно как в версии, которая работала. По управляющему порту
переключается только вторая ступень и дальше: это единственное место, где
действительно происходит смена решения. Tor надёжнее всего делает то, ради чего
его запустили.

Поэтому оба порта теперь выбирает само приложение — привязкой к нулевому порту
и чтением того, что выдало ядро, — и записывает в torrc явными числами. Они
по-прежнему случайные (фиксированный 9050 — первое, что ищут в инструкциях по
поиску средств обхода на телефоне), но не меняются в течение сессии.

Заодно закрыты две гонки помельче: управляющее соединение публикуется
`TorService` до того, как оно аутентифицировано, поэтому первая же команда
возвращала «514 Authentication required» — теперь приложение дожидается, пока
команда действительно пройдёт; и `SETEVENTS` заменяет список, а не дополняет
его, поэтому подписка на события подтверждается ещё раз через пару секунд после
того, как `TorService` сделает свою.

И последнее: длина аргументов моста. Всё, что идёт после отпечатка, tor
передаёт транспорту через поля аутентификации SOCKS5 — а это 2 x 255 байт, и tor
проверяет это при разборе, отвергая строку целиком. Поскольку все мосты одной
ступени ставятся одним `SETCONF`, одна длинная строка роняла всю ступень вместе
с `UseBridges`. Опубликованная строка Snowflake — уже 435 байт, а приложение
добавляет к ней ещё и профили TLS и DTLS. Теперь лишние параметры отбрасываются
по порядку значимости, пока строка не станет приемлемой.

### 4.13. Почему Snowflake летает по Wi-Fi и молчит в мобильной сети

Это не блокировка оператора, это NAT. Данные Snowflake ходят через WebRTC, а
WebRTC нужно, чтобы NAT перед клиентом отдавал **один и тот же публичный порт**
для разных адресатов. Домашние роутеры так и делают. Carrier-grade NAT, за
которым сидит почти любой мобильный абонент, часто выдаёт новый порт на каждое
направление — это симметричный NAT, в терминах Snowflake «restricted».

Клиента с таким NAT брокер может свести только с волонтёрским прокси, у
которого NAT «unrestricted», а большинство волонтёров сидят за такими же
домашними роутерами. Пул подходящих прокси схлопывается — и получается ровно то,
что видно снаружи: по Wi-Fi соединение за секунды, по мобильной сети не
устанавливается никогда.

Приложение теперь это измеряет само. Один UDP-сокет, два разных STUN-сервера,
сравнение выданных адресов: одинаковые — отображение не зависит от адресата,
разные — зависит. Меряется именно с одного сокета; с двух разных портов
результат отличался бы на любом NAT, и все сети выглядели бы симметричными.

Что с этим делается: Snowflake не выбрасывается (совпадение с unrestricted
прокси всё ещё возможно), но уходит вниз лестницы, а WebTunnel и obfs4 —
которым UDP вообще не нужен — поднимаются наверх. На экране маршрутов при этом
написано, почему порядок именно такой.

### 4.14. Почему тоннель «тормозит на простое» и «через десять минут»

Десять минут — это не совпадение, это `MaxCircuitDirtiness`. По умолчанию tor
через это время перестаёт вешать новые потоки на старую цепочку, и следующее
соединение ждёт постройки новой. По прямому каналу это незаметно, через прокси
добровольца — это и есть та самая пауза.

Настройки tor по умолчанию вообще рассчитаны на прямое подключение: десять
секунд на постройку цепочки, дальше таймаут *обучается* по наблюдениям. Через
WebRTC-путь три вещи ломаются разом — постройка не укладывается в таймаут, tor
бросает цепочки, которые почти достроил, и обучение тренируется на этих неудачах,
то есть таймаут не растёт, а сжимается.

Поэтому тайминги цепочек теперь едут вместе с маршрутом и ставятся тем же
`SETCONF`: для брокерных транспортов — 90 секунд на постройку, обучение
выключено, терпение к потокам, и полчаса до ротации цепочек. Полчаса — это
осознанный размен: более долгая цепочка связывает между собой больше действий за
сессию. Для obfs4 и прямого подключения всё остаётся близким к штатному.

Сверх этого:

* пока тоннель поднят, раз в минуту проверяется, что у tor есть запасная
  построенная цепочка, и если нет — она заказывается заранее. Tor перестаёт
  держать запас, когда клиент долго молчит, и тогда первое же действие после
  паузы оплачивает постройку целиком;
* в настройках появилась просьба вывести приложение из-под оптимизации батареи.
  Через несколько минут с погашенным экраном Android начинает придерживать
  фоновую сетевую активность, соединение транспорта с мостом затихает, дальняя
  сторона его закрывает — и всё строится заново. Это и есть самая частая причина
  «работало, а потом перестало»;
* список STUN-серверов в строке Snowflake сокращается до трёх. В опубликованной
  строке их восемь, и WebRTC собирает кандидатов со всех, прежде чем сможет
  что-то предложить брокеру: каждый медленный или мёртвый сервер в этом списке —
  это секунды ожидания до того, как Snowflake вообще начнёт искать прокси.
  Сокращается именно список Tor Project, а не заменяется своим: он подобран под
  то поведение отображения, на которое Snowflake опирается;
* если для этой сети уже известен работавший маршрут, измерение сети целиком
  пропускается. Мерить то, по поводу чего есть подтверждённый ответ, — это время,
  которое пользователь смотрит на прогресс-бар ради сведений, по которым мы всё
  равно не будем действовать;
* первые ступени идут не по очереди, а с разбегом, и побеждает первая ответившая
  (4.17);
* ступень бросается раньше, если tor сам сообщил, что она безнадёжна. Tor
  отправляет не только прогресс, но и отчёты о неудачах со счётчиком попыток;
  маршрут, который проходит рукопожатие и после этого обрывается — почерк
  убитого фронтинга — раньше отнимал минуту таймаута.

  Счётчик у tor общий на весь процесс, а не на маршрут, и первая версия этой
  проверки читала его как есть. Со второй ступени приложение наследовало все
  неудачи первой и списывало маршрут через пару секунд после того, как начинало
  его пробовать. Теперь берётся точка отсчёта в момент смены маршрута, считается
  только прирост, и сверх того требуется, чтобы прогресс уже перестал двигаться:
  медленный транспорт, у которого не выходят первые попытки, пока он ищет
  прокси, — это норма, а не приговор.

### 4.16. Conjure: маршрут, у которого нет адреса

У всех остальных транспортов есть адрес моста, записанный в строке моста, — и
он же есть то, что блокируют. У Conjure его нет.

Клиент регистрируется у станции, работающей внутри сотрудничающего оператора, и
получает «фантом» — адрес в адресном пространстве этого оператора, на котором
никто не слушает. Клиент соединяется с фантомом; станция узнаёт это соединение
по дороге и заворачивает его к себе. Со стороны сети видно соединение с обычным
ничем не примечательным хостом, который просто не отвечает. Заносить в список
блокировки нечего, кроме самого оператора.

Для мобильной сети важно и второе: Conjure — обычный TCP. NAT оператора, из-за
которого Snowflake на мобильном интернете часто не находит подходящего
волонтёра вообще (4.13), к нему отношения не имеет.

Регистрация — самая дорогая часть: это запрос к станции через домен-фронтинг, и
под нагрузкой он занимает десятки секунд. Поэтому SOCKS-соединение выдаётся tor
сразу, а его первые байты придерживаются, пока фантом не поднимется; иначе tor
счёл бы прокси сломанным, а не медленным. Регистрация умеет идти тремя путями, и
приложение везёт с собой две строки моста: через фронтированный API и через DNS.
Второй нужен ровно тогда, когда фронтинг уже убит: ему не нужно ничего, кроме
работающего DNS-over-HTTPS, — а это примерно последнее, что можно отнять у сети,
оставив её сетью.

**Цена интеграции.** Клиент Conjure тянет за собой реестр транспортов, а реестр —
второй, форкнутый экземпляр obfs4. В приложении уже есть lyrebird, у которого
свой потомок того же самого исходного obfs4proxy. Оба регистрируют флаг
командной строки `obfs4-distBias` в инициализаторе пакета. Регистрация одного
имени дважды — это паника, инициализаторы выполняются при загрузке библиотеки, и
на Android это означает, что приложение умирает при запуске — независимо от
того, выбрал ли кто-нибудь Conjure.

Развязка сделана в два шага и записана в коде:

* пакет регистраторов Conjure скопирован в `internal/ptbridge/conjurereg` без
  одного файла на семнадцать строк — обёртки над decoy-регистратором, которая и
  тянет реестр. Этот регистратор приложением не используется;
* сам форк obfs4 всё равно достаётся через `gotapdance`, поэтому он лежит в
  `third_party/obfs4` с единственным изменением относительно апстрима: удалена
  регистрация того самого флага. Переменная, которую он ставил, сохраняет
  значение по умолчанию — то же, что и в апстриме; читать её из командной строки
  на Android всё равно неоткуда.

Обе копии лежат под своими лицензиями, с указанием происхождения и причины.

**Что проверено.** На настоящем tor и настоящей станции: регистрация проходит,
станция отдаёт фантом (`Connected to phantom 148.61.7.130:80 using transport
prefix_GetLong`) и заодно свежий `ClientConf` вместо вкомпилированного, tor
принимает плагин и доходит через него до реле. Полный bootstrap до 100 % в этом
окружении не подтверждён — там на 10 % встают все транспорты, включая заведомо
рабочие, так что это свойство контейнера, а не Conjure.

**Чего это не даёт.** Станции развёрнуты у ограниченного числа операторов, и
путь от абонента до фантома должен проходить через одного из них. Заработает ли
это на конкретном российском провайдере — вопрос покрытия, а не кода. Tor Project
для России рекомендует snowflake, webtunnel и obfs4; Conjure в этот список пока
не входит и лежит в приложении ступенью ниже, а не вместо них.

### 4.19. Почему на мобильной сети не работало ничего

Три факта, которые по отдельности выглядят мелочью, а вместе убирают с лестницы
именно тот транспорт, который на такой сети и должен был работать.

Во-первых, **встроенных мостов WebTunnel нет ни одного** — ни у нас, ни в
публичном списке Tor Project. Их выдают по запросу, поштучно, и это как раз то,
что делает их ценными: их нет ни в одном перечислимом списке. Обратная сторона —
без обращения к сервису мостов их нет и у клиента.

Во-вторых, **транспорт без мостов молча пропускается**. Правильное поведение —
`UseBridges 1` без единого моста это тихий висяк, — но записывалось оно в журнал
на уровне debug, то есть никак.

В-третьих, живой запрос к сервису мостов ждал **шесть секунд**. На нецензурируемой
сети этого хватает. На цензурируемой прямой запрос не проходит вовсе, а
единственный работающий путь — через фронтинг, и он заведомо дольше шести секунд.
То есть ровно там, где свежие мосты решают всё, приложение их не дожидалось.

Итог: на мобильной сети WebTunnel не пробовался никогда. Snowflake там не работает
из-за NAT оператора (4.13), obfs4 упирается в заблокированные адреса, meek
убивают на двадцатом проценте — и оставался Conjure, у которого своя лотерея с
покрытием станций.

Что сделано:

* запрос к сервису мостов больше не блокирует старт и не сдаётся через шесть
  секунд. Он идёт **параллельно с попыткой подключения**, с бюджетом в полторы
  минуты, и то, что вернулось, добавляется в уже идущую попытку — это стало
  возможно ровно потому, что маршруты теперь умеют добавляться к работающему tor
  (4.17);
* маршрут, присоединившийся поздно, получает **свой** бюджет времени. Иначе
  мосты приезжали бы аккурат к моменту, когда попытку пора бросать;
* пропуск транспорта из-за отсутствия мостов пишется в журнал заметно;
* адреса из документационных диапазонов больше не считаются настоящими.
  WebTunnel публикуется как `[2001:db8:...]:443`, где реальная точка входа — в
  `url=`. Раньше приложение честно пробовало соединиться с адресом, который
  никогда никому не отвечал, и заносило его в карантин за это;
* когда сервис мостов недоступен, приложение так и говорит — и отправляет
  добавить мосты вручную, вместо «перепробованы все маршруты».

**Чего сознательно не сделано:** мосты WebTunnel не зашиты в приложение. Их
выдают поштучно именно потому, что публичный список перечисляется и блокируется
за день; положить пару штук в APK — значит сжечь их для всех, кто их получил.
Правильный путь — чтобы приложение умело их достать, и ручное добавление как
запасной выход.

### 4.17. Что взято у Mullvad

Обфускация Mullvad неотделима от их серверов: udp2tcp, Shadowsocks, QUIC и LWO —
это всё способы завернуть WireGuard по дороге к машине Mullvad. Копировать тут
нечего. А вот две вещи из их архитектуры переносятся напрямую, и обе — про то,
как принимается решение, а не про то, что именно шифруется.

**Мультиплексор.** В `tunnel-obfuscation/src/multiplexer.rs` их клиент не
пробует один способ, ждёт его провала и переходит к следующему. Он поднимает
транспорты **с интервалом в секунду**, отправляет одинаковый трафик во все и
оставляет тот, который первым ответил. Ожидание провала — это время, потраченное
без единого бита новой информации.

Tor можно вести так же, потому что мосты — это список, и он пробует те, что у
него есть. Проверено на tor 0.4.8: `SETCONF` с добавленным мостом, пока первый
ещё пробуется, принимается, первый не трогает и сразу запускает соединение с
новым (`orconn-status` показывает `LAUNCHED` на добавленном отпечатке через
секунды). Поэтому первые ступени лестницы теперь стартуют не по очереди, а с
разбегом в шесть секунд, и побеждает тот, через кого tor загрузился.

Разбег — не вежливость. Веер одновременных рукопожатий сам по себе один из
сигналов, по которым работает нынешний DPI (4.1, 4.3), поэтому в гонке участвуют
только маршруты **разные по природе**: три моста obfs4 разом выглядят ровно тем,
чем являются, а HTTPS-соединение, WebRTC-сессия и соединение с фантомом, который
не отвечает, — это три несвязанные вещи.

Кто именно победил, спрашивается у tor через `orconn-status` и сопоставляется по
отпечатку из строки моста. Без этого гонка ничему не учит: смысл памяти по сетям
в том, чтобы знать, какой из способов сработал, а не что «что-то сработало».

**Монитор офлайна.** У Mullvad это отдельный компонент, и по делу: устройство без
сети провалит все маршруты, а сказать про это «блокировка» — значит отправить
человека искать не там. Теперь это проверяется первым, до всего остального.

**Чего не взято.** DAITA — их защита от анализа трафика — решает ту же задачу,
что `ConnectionPadding` у tor, который уже включён (4.10); вторым слоем поверх
Tor это стоило бы трафика без выигрыша. Ротация способов доступа к их API у нас
уже была в упрощённом виде: запрос к сервису мостов сначала идёт напрямую, а при
неудаче — через фронтинг.

### 4.18. Самопроверка

Неудачное подключение способно сказать только «перепробованы все маршруты» — это
правда и это бесполезно. Оно не отличает сеть, которая блокирует всё, от
транспорта, который не запустился, от пустого списка мостов, от tor, который не
принял собственную конфигурацию. Лечится это всё по-разному, а с телефона в
другой стране разница иначе не видна.

Поэтому в «Диагностике» есть кнопка, которая прогоняет каждый этап отдельно и
пишет в журнал, что нашла: есть ли сеть вообще; какие транспорты поднялись и на
каких портах; сколько мостов есть по каждому; отвечает ли сервис мостов; что
показывает измерение сети и NAT; принимает ли tor конфигурацию и отвечает ли его
управляющий порт. Подключение при этом не устанавливается.

### 4.15. Язык интерфейса

Весь текст, который видит человек, теперь лежит в ресурсах и переведён. Это
касается не только экранов: описания транспортов, профилей Client Hello, режимов
изоляции и DNS раньше были константами в коде, а строки сетевых измерений
собирались прямо в слое, у которого нет и не должно быть `Context`. Последние
передаются наверх как идентификатор ресурса с аргументами и превращаются в слова
уже там, где есть кому их прочитать — заодно это правильно отрабатывает смену
языка телефона на живом тоннеле.

Подписи нижней навигации больше не переносятся на вторую строку: слот в панели
делится поровну, слово длиннее девяти знаков ломается пополам и обрезается по
высоте. Многоточие для навигации не годится — подпись там единственное, что
называет раздел, — поэтому текст держится в одну строку и при необходимости
чуть уменьшается.

## 5. Утечки

Обход блокировок бесполезен, если трафик течёт мимо туннеля.

* **UDP.** Tor умеет только TCP. Весь не-DNS UDP отбрасывается на границе
  туннеля (`BlockUDP`), а не выпускается наружу. QUIC и WebRTC при этом
  откатываются на TCP. Счётчик отброшенных датаграмм виден на главном экране.
* **DNS.** Запросы никогда не уходят резолверу локальной сети. Три режима, все
  внутри туннеля: `DNSPort` самого tor (разрешение на выходном узле),
  DNS-over-TCP через SOCKS, DNS-over-HTTPS (RFC 8484) через SOCKS. Работа идёт
  прямо в wire-формате, поэтому DNS нигде не парсится.
* **IPv6.** Интерфейс забирает и `::/0`. Без этого IPv6-трафик в
  IPv6-способной сети просто прошёл бы мимо VPN.
* **Kill switch.** При включённом переключателе интерфейс поднимается
  **сразу**, ещё до того, как выбран маршрут: читателя у дескриптора нет,
  пакеты просто исчезают. Это настоящий kill switch, а не обещание.
* **`.onion`.** В torrc включён `AutomapHostsOnResolve` с суффиксом `.`, а
  виртуальная сеть `10.192.0.0/10` явно маршрутизируется в TUN. Без этого
  прозрачное проксирование резолвит имена на выходе и подключается по голому
  IP, что ломает всё, что живёт за CDN, и убивает изоляцию цепочек по имени.
* **Изоляция цепочек.** Логины SOCKS5 генерируются по-разному в зависимости от
  режима, и `IsolateSOCKSAuth` в tor разводит их по разным цепочкам: одна общая,
  одна на сайт (как в Tor Browser), одна на соединение.
* Логи живут только в памяти, бэкапы приложения отключены в манифесте.

## 6. Сборка

Нужны Android SDK (platform 37, build-tools 37) и JDK 17+.

```bash
cd android
echo "sdk.dir=/path/to/android-sdk" > local.properties
./gradlew :app:assembleDebug
# APK: app/build/outputs/apk/debug/
```

Релиз подписывается ключом из окружения, ничего секретного в репозитории нет:

```bash
export VEIL_KEYSTORE=/path/to/keystore.jks
export VEIL_KEYSTORE_PASSWORD=... VEIL_KEY_ALIAS=... VEIL_KEY_PASSWORD=...
./gradlew :app:assembleRelease
```

Собираются отдельные APK на `arm64-v8a`, `armeabi-v7a`, `x86_64` плюс
универсальный. Для обычного телефона нужен `arm64-v8a`.

### Нативный слой

`app/libs/veiltun.aar` собран из `android/native/veiltun` (Go + gVisor) и
содержит **и** туннель, **и** pluggable transports. Это не стилистический
выбор: две gomobile-библиотеки в одном приложении несут каждая свой
`libgojni.so` и свою копию `go.Seq`, и загрузится только одна из них. Поэтому
контроллер транспортов из IPtProxy (MIT) вендорится в
`native/veiltun/internal/ptbridge` — у апстрима в `go.mod` локальный `replace`
для dnstt, который нельзя разрешить извне; сам dnstt удалён, остальное не
тронуто.

Пересобрать:

```bash
cd android/native/veiltun
export ANDROID_NDK_HOME=$ANDROID_HOME/ndk/28.2.13676358
go install golang.org/x/mobile/cmd/gomobile@latest
gomobile init
gomobile bind -target=android/arm64,android/arm,android/amd64 -androidapi 24 \
  -javapkg=app.veil.tun -ldflags="-s -w -checklinkname=0" \
  -o ../../app/libs/veiltun.aar .
```

`-checklinkname=0` обязателен: `wlynxg/anet`, который тянет за собой
pion/webrtc (нужный Snowflake), использует `go:linkname` на внутренности
пакета `net`, и без этого флага 32-битный ARM не линкуется.

Сам `tor` подтягивается готовым из Maven Central
(`info.guardianproject:tor-android`) — его собирать не нужно.

## 9. Честные ограничения

* Проверено в поле частично. Snowflake подключается; meek на российской сети
  доходит до 20 % и там же обрывается через десяток секунд — это почерк убитого
  фронтинга, и это же говорит про Россию сам Tor Project: в его рекомендациях
  для `ru` meek не значится вовсе (там snowflake, webtunnel, obfs4). Мы meek не
  убираем — он остаётся рабочим в других странах, — но на такой сети он теперь
  отбрасывается за секунды, а не за минуту.
* Сама архитектура (внешний `ClientTransportPlugin ... socks5`, переключение
  маршрута по управляющему порту, фиксированные порты) проверена на настоящем
  tor: транспорт поднимается, tor через него доходит до реле. Остальное —
  логика проб и порядка ступеней — по-прежнему требует калибровки в поле.
* Snowflake в мобильной сети — отдельная история, и не наша: за carrier-grade
  NAT он часто не находит подходящего волонтёра вообще (см. 4.13). Приложение
  это измеряет и перестраивает порядок, но сделать WebRTC работающим за
  симметричным NAT оно не может — там ответом будет WebTunnel.
* Пороги из раздела 4 (три параллельных хендшейка, 350–400 мс, ~120 и ~600
  секунд штрафа) — рабочие гипотезы из публичных разборов, а не измеренные нами
  константы. Мы закладываемся на запас в безопасную сторону; если реальные
  значения другие, менять надо только числа в `HandshakeGovernor` и
  `EndpointCooldown`.
* Обход по именам (`.ru` и прочие) сознательно отдаёт локальной сети список
  того, чем вы пользуетесь. Это не баг, это цена за работающий банк — поэтому
  выключено по умолчанию и подписано прямо в интерфейсе.
* Слушающие порты на loopback закрыть полностью пока нельзя: `ClientTransportPlugin`
  у tor принимает только TCP-адрес, а unix-сокет для SocksPort ломает встроенный
  `TorService`. Что именно остаётся открытым — видно на экране «Диагностика».
* Tor медленный. Через meek и Snowflake — очень медленный. Это свойство
  маршрутов, а не приложения.
* Полная анонимность требует не только транспорта: приложение защищает
  сетевой уровень, но не мешает установленным приложениям самим себя выдать.
* Conjure реализован (4.16), но его станции развёрнуты у ограниченного числа
  операторов: заработает ли он на конкретном провайдере — вопрос покрытия сети,
  а не кода. Psiphon по-прежнему только описан.
* Ради Conjure в дереве лежат две копии чужого кода: регистраторы Conjure и
  форк obfs4 с удалённой регистрацией флага. Обе — с лицензиями и объяснением
  причины, но это код, который придётся обновлять руками.
* Автотестов нет: критическая часть логики — сетевое поведение, которое имеет
  смысл проверять интеграционно, а не юнит-тестами на моках.
