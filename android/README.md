# Veil — VPN на свободных протоколах

Android-приложение, которое поднимает системный VPN и уводит весь трафик
устройства в сеть Tor, автоматически подбирая способ обхода блокировки.
Ничего вводить не нужно: ни адрес сервера, ни ключ, ни логин. Всё, что
использует приложение, — свободное ПО и публичная инфраструктура.

Интерфейс написан по Material 3 Expressive (Compose Material3 1.5.x): морфинг
формы у главной кнопки, пружинная моторика `MotionScheme.expressive()`,
`ShortNavigationBar`, `MediumFlexibleTopAppBar`, `ButtonGroup`,
`LoadingIndicator`, динамическая палитра Material You. `compileSdk`/`targetSdk`
— 37.

## 1. Что тут вообще происходит

```
   приложения на телефоне
            │  IP-пакеты
            ▼
   ┌────────────────────┐
   │  VpnService (TUN)  │  10.55.0.1/24, маршрут 0.0.0.0/0 и ::/0
   └─────────┬──────────┘
             │ file descriptor
             ▼
   ┌────────────────────────────────────────────┐
   │  veiltun (Go + gVisor netstack)            │
   │  · терминирует TCP, отдаёт в SOCKS5        │
   │  · DNS перехватывает и уводит внутрь       │
   │  · UDP отбрасывает (Tor его не умеет)      │
   └─────────┬──────────────────────────────────┘
             │ SOCKS5 127.0.0.1:9050
             ▼
   ┌────────────────────┐      ┌──────────────────────────────┐
   │  tor (libtor.so)   │◄────►│ lyrebird / snowflake         │
   │  control port      │  PT  │ obfs4 · meek · webtunnel     │
   └─────────┬──────────┘      └──────────────────────────────┘
             │                   (в том же libgojni.so, что и veiltun)
             ▼
        сеть Tor
```

Ключевая деталь: собственный пакет приложения исключён из VPN
(`addDisallowedApplication`). Иначе сокеты самого tor и транспортов ушли бы
обратно в тот же туннель, который они должны питать, и не поднялось бы ничего.

## 2. Что работает «из коробки», без ввода серверов

Вопрос «какие ещё стандарты можно внедрить, чтобы работало без вбивания
данных» на практике сводится к одному критерию: **у протокола должна быть
публичная инфраструктура, адреса которой уже зашиты в клиент**. Таких
вариантов немного.

### Реализовано

| Маршрут | Что прячет | Откуда берёт адреса | Цена |
|---|---|---|---|
| **Tor напрямую** | ничего | директории-авторити зашиты в `tor` | быстрый |
| **obfs4** (lyrebird) | сигнатуру протокола | встроенные мосты + Moat API | быстрый |
| **WebTunnel** | всё внутри обычного HTTPS к живому сайту | мосты из Moat / вручную | средний |
| **meek_lite** | domain fronting через CDN | URL и front зашиты | медленный |
| **Snowflake** | нет постоянного адреса вообще | брокер + domain fronting / AMP-кэш | медленный |

Все пять не требуют от пользователя ни одного поля ввода. Списки встроенных
мостов лежат в `app/src/main/assets/builtin_bridges.json` (снимок с
`bridges.torproject.org/moat/circumvention/builtin`) и обновляются на лету
при каждом подключении.

### Почему не WireGuard, Shadowsocks, VLESS, Hysteria и подобное

Это транспорты «точка-точка»: они прекрасны, но требуют сервера, которого у
пользователя нет. Без адреса и ключа их нельзя запустить в принципе. Из них
нельзя сделать «нажал кнопку и работает», можно только «нажал кнопку и
подключился к чужому серверу», а это уже совсем другой продукт с другой
моделью доверия. Архитектура приложения (`TransportEngine` → локальный
SOCKS5) оставляет для них место, но по умолчанию они не включены.

### Что рассматривалось и не вошло

* **Psiphon** — единственный реальный кандидат «второй сети из коробки»:
  открытый код (GPLv3), встроенный список серверов, работает без настройки.
  Не включён: требует собственных `PropagationChannelId`/`SponsorId` от
  Psiphon Inc. и завязан на централизованно управляемую сеть. Архитектурно
  добавляется одним классом-движком.
* **Conjure** (refraction networking) — сильнее Snowflake по устойчивости, но
  клиент не входит в IPtProxy, потребовалась бы отдельная сборка Go-модуля.
* **I2P** — не заменяет VPN: наружу ходит только через редкие outproxy.
* **Lantern** — не полностью открыт.

## 3. Как приложение борется с блокировкой

Это основная содержательная часть, а не просто «включили Tor».

### 3.1. Сначала измеряем сеть, потом выбираем

`net/Probe.kt` параллельно проверяет пять вещей и делает это **настоящими
сетевыми пробами**, а не догадками:

1. **TCP до директорий Tor** — маршрутизируется ли протокол вообще.
2. **TCP до опубликованных obfs4-мостов** — не выжжены ли адреса по IP.
3. **TCP до крупных CDN** (`www.phpmyadmin.net`, `app.datapacket.com`) —
   жив ли путь, который нужен meek и Snowflake.
4. **Полный TLS-хендшейк к `www.torproject.org`** — если TCP открывается, а
   рукопожатие рвётся, это классическая подпись фильтрации по SNI.
5. **STUN binding request по UDP** — жив ли UDP; без него у Snowflake нет
   канала данных.

Из этих пяти ответов строится ранжирование маршрутов (`NetworkProbe.rank`).

### 3.2. Лестница эскалации

`tor/StrategyPlanner.kt` собирает порядок попыток из четырёх источников, по
убыванию силы:

1. **Что уже работало в этой конкретной сети.** `data/StrategyMemory.kt`
   помнит результат по непрозрачному отпечатку сети. Отпечаток строится из
   типа транспорта, DNS-серверов линка и MCC SIM-карты и сразу хешируется —
   разрешение на геолокацию (которое понадобилось бы для SSID) не
   запрашивается вообще.
2. **Что Tor Project рекомендует для этой страны.** Те же данные, что
   использует Tor Browser Connect Assist:
   `moat/circumvention/settings`. Оффлайн-снимок лежит в
   `assets/circumvention_map.json`.
3. **Результаты проб** из пункта 3.1.
4. **Статическая лестница** — от дешёвого к дорогому, чтобы неверная догадка
   выше по списку никогда не выкидывала рабочий маршрут.

Последней ступенью всегда идёт Snowflake, а после него — Snowflake с
рандеву через **AMP-кэш Google** вместо domain fronting: это выживает там, где
заблокирован уже сам фронтированный запрос к брокеру.

### 3.3. Бюджет времени и детектор «залипания»

Каждой ступени даётся свой бюджет (`StrategyPlanner.budgetMillis`): obfs4 —
60 с, meek — 90 с, Snowflake — 120 с. Это не произвол: obfs4 либо
подключается быстро, либо не подключается вовсе, а Snowflake сначала должен
найти волонтёрский прокси и штатно тратит полминуты до первого байта.
Обрубить Snowflake по бюджету obfs4 — классический способ ошибочно решить, что
не работает ничего.

Плюс отдельно отслеживается **отсутствие прогресса**: если процент bootstrap
не двигается 35 секунд, ступень признаётся мёртвой досрочно. Именно это
отличает инструмент, который честно перебирает варианты, от того, что пять
минут показывает «10 %».

### 3.4. Когда и мосты не работают

Встроенные мосты публичны, поэтому цензор перечисляет и блокирует их первыми.
Ответ на это — три уровня:

* **Обновление списка** с `moat/circumvention/builtin` при каждом коннекте.
* **Запрос приватных мостов через CAPTCHA прямо в приложении**
  (`moat/fetch` + `moat/check`). Это важно именно тогда, когда сайт
  `bridges.torproject.org` недоступен: решать капчу в приложении можно, а
  открыть сайт — нет.
* **Фронтированный запрос к самому API.** Если прямой HTTPS к Moat не проходит,
  запрос повторяется **через meek**: приложение поднимает lyrebird, само
  открывает SOCKS5-соединение и кладёт аргументы транспорта в поля
  username/password ровно так, как это делает tor (`net/Socks5.kt`,
  `SocksProxy.withTransportArgs`). Дальше поверх этого сокета вручную
  говорится HTTPS (`net/SimpleHttp.kt`), потому что штатный HTTP-клиент
  Android не даёт задать SOCKS-креденшелы.

И, наконец, Snowflake: у него **нет постоянного адреса, который можно
заблокировать**. Именно поэтому он последний в лестнице, а не первый — он
работает почти всегда, но медленно.

### 3.5. Отдать канал другим

В настройках есть переключатель «работать прокси Snowflake»: устройство
становится одним из тех волонтёрских узлов, через которые кто-то за файрволом
дотягивается до Tor. Это единственное, чем пользователь без цензуры может
напрямую помочь пользователю с цензурой.

## 4. Утечки

Обход блокировок бесполезен, если трафик течёт мимо туннеля.

* **UDP.** Tor умеет только TCP. Весь не-DNS UDP отбрасывается на границе
  туннеля (`BlockUDP`), а не выпускается наружу. QUIC и WebRTC при этом
  откатываются на TCP. Счётчик отброшенных датаграмм виден на главном экране.
* **DNS.** Запросы никогда не уходят резолверу локальной сети. Три режима, все
  внутри туннеля: `DNSPort` самого tor (разрешение на выходном узле),
  DNS-over-TCP через SOCKS, DNS-over-HTTPS (RFC 8484) через SOCKS. Работа идёт
  прямо в wire-формате, поэтому DNS нигде не парсится.
* **IPv6.** Интерфейс забирает и `::/0`. Без этого IPv6-трафик в
  IPv6-способной сети просто прошёл бы мимо VPN.
* **Kill switch.** При включённом переключателе интерфейс поднимается
  **сразу**, ещё до того, как выбран маршрут: читателя у дескриптора нет,
  пакеты просто исчезают. Это настоящий kill switch, а не обещание.
* **`.onion`.** В torrc включён `AutomapHostsOnResolve` с суффиксом `.`, а
  виртуальная сеть `10.192.0.0/10` явно маршрутизируется в TUN. Без этого
  прозрачное проксирование резолвит имена на выходе и подключается по голому
  IP, что ломает всё, что живёт за CDN, и убивает изоляцию цепочек по имени.
* **Изоляция цепочек.** Логины SOCKS5 генерируются по-разному в зависимости от
  режима, и `IsolateSOCKSAuth` в tor разводит их по разным цепочкам: одна общая,
  одна на сайт (как в Tor Browser), одна на соединение.
* Логи живут только в памяти, бэкапы приложения отключены в манифесте.

## 5. Сборка

Нужны Android SDK (platform 37, build-tools 37) и JDK 17+.

```bash
cd android
echo "sdk.dir=/path/to/android-sdk" > local.properties
./gradlew :app:assembleDebug
# APK: app/build/outputs/apk/debug/
```

Релиз подписывается ключом из окружения, ничего секретного в репозитории нет:

```bash
export VEIL_KEYSTORE=/path/to/keystore.jks
export VEIL_KEYSTORE_PASSWORD=... VEIL_KEY_ALIAS=... VEIL_KEY_PASSWORD=...
./gradlew :app:assembleRelease
```

Собираются отдельные APK на `arm64-v8a`, `armeabi-v7a`, `x86_64` плюс
универсальный. Для обычного телефона нужен `arm64-v8a`.

### Нативный слой

`app/libs/veiltun.aar` собран из `android/native/veiltun` (Go + gVisor) и
содержит **и** туннель, **и** pluggable transports. Это не стилистический
выбор: две gomobile-библиотеки в одном приложении несут каждая свой
`libgojni.so` и свою копию `go.Seq`, и загрузится только одна из них. Поэтому
контроллер транспортов из IPtProxy (MIT) вендорится в
`native/veiltun/internal/ptbridge` — у апстрима в `go.mod` локальный `replace`
для dnstt, который нельзя разрешить извне; сам dnstt удалён, остальное не
тронуто.

Пересобрать:

```bash
cd android/native/veiltun
export ANDROID_NDK_HOME=$ANDROID_HOME/ndk/28.2.13676358
go install golang.org/x/mobile/cmd/gomobile@latest
gomobile init
gomobile bind -target=android/arm64,android/arm,android/amd64 -androidapi 24 \
  -javapkg=app.veil.tun -ldflags="-s -w -checklinkname=0" \
  -o ../../app/libs/veiltun.aar .
```

`-checklinkname=0` обязателен: `wlynxg/anet`, который тянет за собой
pion/webrtc (нужный Snowflake), использует `go:linkname` на внутренности
пакета `net`, и без этого флага 32-битный ARM не линкуется.

Сам `tor` подтягивается готовым из Maven Central
(`info.guardianproject:tor-android`) — его собирать не нужно.

## 6. Карта кода

```
model/          Transport, TunnelState, BridgeLine
core/           кольцевой лог в памяти, форматирование
data/           настройки (DataStore), мосты, отпечаток сети, память стратегий
net/            SOCKS5-клиент, минимальный HTTPS, Moat API, активные пробы
tor/            генератор torrc, запуск транспортов, control port, планировщик
vpn/            VpnService, шина состояния, уведомления, плитка, автозапуск
ui/             тема, компоненты, экраны (Compose Material 3 Expressive)
native/veiltun/ Go: gVisor netstack → SOCKS5, DNS, защита от утечек UDP
```

## 8. Честные ограничения

* Приложение не проверялось на реальной цензурируемой сети — логика проб и
  эскалации написана по документированному поведению транспортов, но
  калибровать бюджеты и пороги надо в поле.
* Tor медленный. Через meek и Snowflake — очень медленный. Это свойство
  маршрутов, а не приложения.
* Полная анонимность требует не только транспорта: приложение защищает
  сетевой уровень, но не мешает установленным приложениям самим себя выдать.
* Conjure и Psiphon описаны выше как варианты, но не реализованы.
* Автотестов нет: критическая часть логики — сетевое поведение, которое имеет
  смысл проверять интеграционно, а не юнит-тестами на моках.
